# 進行方向の案内：実データでの確認（Issue #22）

判定規則の全体は [navigation-guidance-plan.md](../navigation-guidance-plan.md) の4章にある。本書は、その規則を実データで調整した経緯と結果を記録する。

## 1. まとめ

- 実 release の300件はすべて成功した。処理時間の増加は、M5 の記録の範囲に収まった。
- 右折・左折の向きは、形状の前後30mの方位変化と99.6%以上で一致した（目安98%以上）。
- 自動車の50か所を目視し、向きの誤りは0件、直進に近い余分な `slight` は4件（8%）だった（目安：誤案内10%以下）。
- 1kmあたりの案内数の中央値は、徒歩5.30、自転車3.80、自動車1.10である。
- **実機GPSでは確認していない。** 判定は Claude 1人が地理院地図で行った（7章）。

### 実 release の検査（最終）

## 4. 調整した規則

| 見つかった問題 | 変更 | テスト |
|---|---|---|
| 一方通行の道路へのT字路で、他に進める道路がないため案内が抜ける | 逆向きにしか通れない道路（`one_ways`）を、目に見える分岐として数える。道なりの判定も両方を見る。分岐（fork）の判定は `others` だけを見る | `t7_t_junction_onto_a_one_way_road_is_right`、`t7_one_way_road_merging_at_a_small_angle_is_not_a_fork` |
| 始点の近くは手前の方位を測れず、向きを誤る | 連の先頭が始点から10m未満の案内を省く（`START_SUPPRESS_M`） | `t7_turn_right_after_the_start_is_arrive_only` |
| 本線を走るだけで、ランプの出口を `slight` と案内する | 出る辺が `_link` でなければ、`_link` の出口を分岐に数えない | `t7_passing_a_ramp_on_the_main_road_is_arrive_only`、`t7_leaving_on_a_ramp_keeps_the_side_of_the_ramp` |
| ほぼ直進で脇道を通るだけなのに `slight` と案内する | `|a|<10°` のときは、分岐の相手を20°未満の出口に絞る（`STRAIGHT_MAX_DEG`、`STRAIGHT_FORK_MAX_DEG`） | `t7_straight_past_a_side_road_at_thirty_five_degrees_is_arrive_only` |
| クランクで `slight` の向きが逆になる | `|a|≥10°` なら連全体の角度の符号で向きを決める | `t7_fork_direction_follows_the_whole_run_at_a_jog` |

この後、コードレビュー（GPT-6.1 Sol）の指摘で、環状交差点の連に出口の先のノードが入る問題を直した。環を出た後のノードは環の連に加えず、環の直後の連は手前の方位を環の出口より前で測らない（テスト：`long_roundabout_keeps_the_step_at_its_exit_past_a_nearby_side_road`、`short_roundabout_does_not_merge_a_turn_just_after_its_exit`）。

`TURN_MIN_DEG` などの既存の定数は変えていない。手段ごとに値を分ける必要はなかった。徒歩の案内量は定数を変えるほどの水準ではないと判断した。

### 取りこぼし候補の内訳

「形状が60°以上曲がるのに30m以内に案内がない地点」を、最寄りのノードの種類で分類した（最終規則）。

| 分類 | 徒歩 | 自転車 | 自動車 |
|---|---|---|---|
| 近くにノードがない（形状の曲がりだけ） | 55 | 222 | 135 |
| 分岐のないカーブ | 23 | 59 | 28 |
| その手段では通れない道路だけの分岐 | 1 | 39 | 30 |
| 分岐はあるが案内なし | 19 | 35 | 27 |
| 一方通行（調整前：自転車80、自動車90） | 0 | 2 | 2 |
| 別の案内の連に含まれる（`slight` など） | 6 | 8 | 3 |
| 合計 | 104 | 365 | 225 |

このうち案内があるべきかを確かめる必要があるのは、「分岐はあるが案内なし」「一方通行」「別の案内の連に含まれる」で、自動車32件（曲がり地点の1.2%）、自転車45件（1.3%）、徒歩25件（1.8%）である。いずれも目安の5%以下に収まる。

目視した「分岐あり案内なし」の中心は、連の角度が30〜60°の道なりとS字で、案内なしで妥当だった。この割合は分類の上限で、実際の取りこぼし率を測ったものではない。

## 6. 符号の不一致（9件）

| 経路 | 案内 | 位置 | 前後30mの方位変化 |
|---|---|---|---|
| `chiba-walk-0018` route-1 | right | 37.4m | −8.4° |
| `saitama-bike-0004` route-2 | right | 1062.6m | −6.9° |
| `saitama-walk-0005` route-2 | right | 2297.3m | −1.7° |
| `saitama-walk-0013` route-4 | right | 1560.6m | −1.9° |
| `tokyo23-car-0006` route-2 | left | 32.1m | +86.6° |
| `tokyo23-walk-0012` route-1 | right | 1818.3m | −10.7° |
| `tokyo23-walk-0013` route-1 | left | 1083.2m | +6.4° |
| `tokyo23-walk-0022` route-3 | right | 1134.7m | −8.9° |
| `tokyo23-walk-0022` route-3 | left | 3094.0m | +31.7° |

多くは徒歩の横断のような長い連で、連全体の角度と±30mの窓の差である。ただし次の2件は、短い距離で何度も曲がる経路で、案内の向きと案内地点の曲がりが食い違う。

- `tokyo23-car-0006` の32.1m：連全体は左へ向かうが、案内地点のノードでは右へ鋭く曲がり、そのまま小さく回る。
- `tokyo23-walk-0022` の3094.0m：8〜40mの辺で右回りに1周する形（歩道橋の階段と思われる）。

判定は「向きは連全体、位置は局所角が最大のノード」としているため、こうした形では利用者の見た目と合わないことがある。頻度が低い（右左折8,965件のうち9件、0.1%）ので規則は変えていない。

## 7. 画面の確認（T8）

実 release のサーバと `VITE_API_MODE=live VITE_ENABLE_SIMULATION=true` のビルドを、Chromium の 390px と 1440px で模擬走行した。住所検索だけは提供元のキーがないため固定の応答に差し替え、経路検索は実サーバへ送った。

コンソールのエラーはなかった（地図タイルの読み込みの失敗は集計から除いた）。

8倍速では、走行中に「位置を確認中」が0.6秒ほど何度か挟まり、その間は案内が消える。照合の保留による表示で、本 Issue では照合のコードを変えていない。

## 8. 限界

- 実機GPSでは確認していない。案内のタイミングや、GPSの誤差で案内が前後する様子は、模擬走行ではわからない。
- 目視の判定は Claude 1人が地理院地図で行った。別の人の確認はない。
- 地図では車線単位の分岐を確認できない。`slight` の妥当性は、道路の形から判断した。
- 右左折禁止の規制は使っていない。道路名も案内に含めない。
- 4地域の300件の結果である。全国の他の地域では確認していない。
- 旧方式（schema 2）の release では `arrive` 1件だけを返すため、案内は「経路に沿って進む」のままになる。
