## 6. 推測で決めた点・計画から外れた点

1. **③の検査の変更（利用者の判断）**：`api/route_response.rs` の `check_outcome` は「事故0件なら `weighted_risk`・死傷者・高リスク区間がすべて0」を求めていた。一方 behavior.md 7章と計画書11.1節は、新方式のモデルの値は事故0件でも正になると定めている。M0で固定した契約どうしが食い違っていて、実データの300件中138件が500 internal_error になった。利用者に確認し、`weighted_risk` を条件から外した（死傷者と高リスク区間の検査は残す）。既存の `tests/api_route_dto.rs` の「事故0件なのに」のケースは、`weighted_risk` だけを残す壊し方では検査に当たらなくなる。そこで、死傷者を1人残す壊し方に替え、同じ検査が働くことを確かめるようにした。メッセージは「事故0件なのに死傷者・高リスク区間がある」に変わった（ケースが照合する「事故0件なのに」は同じ）。**③の範囲の変更なので、③の担当者の確認が必要。**
   フロントの `frontend/src/api/validate.ts` にも同じ条件があり、M4.6 の画面で事故0件の候補を含む検索が「応答を読み取れませんでした」になった。利用者に確認し、同じく `weighted_risk` を条件から外した。`validate.test.ts` に、事故0件で推定リスクが正の応答を受け付け、死傷者が残る応答は拒否する試験を足した。**frontend/ の変更なので、①の担当者の確認が必要。**
2. **`load_calendar` の変更**：`data/load.rs` の `load_holiday_calendar` が schema 2しか受け付けず、schema 3の release ではサーバが起動しなかった。祝日表の置き方と metadata は両 schema で同じなので、2と3を受け付けるようにした。schema 3で `load_calendar` を呼ぶ試験を足した。
3. evaluate の性能：Flash の実装は、事故ごとにsidの番号を経路の先頭から数え直し、クラスタの事故ごとに経路を走査していた。指示役が、線分ごとの先頭sidを1回だけ求め、クラスタのsidをクラスタごとに1回だけ求めるように直した（結果は同じ）。
4. 間引いた経路でのクラスタの事故は、全小線分から最寄りのsidを選ぶ（behavior.md 7章が許す簡略化）。同じ事故が同じ辺に複数当たる場合の最後の同点処理は、`pos_dm` が小さいものを残す。
5. `DatasetInfo.load_seconds` は、右左折禁止の照合器を作る前までの時間（照合器は `RoutingEngine::new` で作る）。照合器を含めた起動の時間は5.1節のとおり4秒程度。
6. `write_routing_test_release(dir)` の `dir` は出力の根で、release は `dir/releases/<release_id>` にできる（`package_routing_release` に合わせた）。
7. schema 3の読込では、metadata の `data_years` と事故CSVから求めた年度を照合する（schema 2の既存の挙動は変えていない）。
