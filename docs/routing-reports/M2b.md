## 3. 推測で決めた点

1. 交差点（道路形状1・31）の事故は、30m以内のクラスタがあればクラスタだけに配分し、なければ辺に進む。交差点付近・単路・踏切は辺に配分する。
2. 番号の照合は国道だけ。主要地方道・一般県道の路線コード上4桁は通し番号で、県道番号と一致しないことを実データで確かめた（一致は36〜40%）。
3. 双子は1組の候補として扱い、近い方の辺に重みを載せ、もう一方に `MIRROR` で写す。
4. 0.1未満を捨てた後に再正規化しない（合計は1以下）。
5. 重みの不足（理由3）が0件になった。正規化だけで配分するため、遠い候補でも重みが残る。「どの候補でもない」という仮説を足す方法があるが、仕様から外れるので入れていない。人の確認の結果で判断する。
6. `PARAMS` の構造（`rules_version: "jp-assign-1"`、尤度表など）は作業役が決めた。形式書13章への追記が必要。
7. 索引 `EdgeAccidentIndex` は約145MBで、形式書17章の見積もり（70〜100MB）より大きい（辺の開始位置の表が約81MB）。M4のメモリの見積もりに反映する。

## 4. 人の確認の手順

**利用者の判断で、確認の方法を変えた（2026-11-03）。** 当初の手順（200件を「正しい／誤り／判断できない」で判定し、最大の重みが0.8以上の群の正解率85%を基準にする）は、負担が大きく判断も難しいため、次のとおりにした。

- 対象：200件のうち、割り当てがあり、高速・自専道のコードでなく、最大の重みが0.8未満か、重み最大の候補が10m超の **要確認36件だけ**。無作為の抜き取りはしない。
  - 高速・自専道は、自動検査（`data/work/M2/review/auto_checks.md`）で上下線の双子とMIRRORを全国で調べる。
  - 未割り当ては外す。
  - 双子の多対多化の後の割り当てでは、36件のうち4件（事故ID 27755、237634、1121993、1757974）が要確認の基準を外れたが、そのまま残した。
- 質問：「事故はどの道（または交差点）で起きたと思うか」を、番号付きの候補から選ぶ（キー1〜9・A〜C、0はどれでもない、Uは分からない）。割り当て先は回答するまで見せず、地図の横に属性の一致の印を出す。
- 基準の変更：0.8以上の群の正解率は人の判定では測らず、機械の指標（国道の番号の一致率98.8%、重み最大の候補までの距離が5m以内の割合71%など）で代える。要確認36件の判定は、決まったパターンの誤りがあるかを見るのに使う。

手順：

1. `data/work/M2/review/index.html` をブラウザで開く（`file://` で動く。外部への通信は、地理院タイルとLeaflet 1.9.4の取得だけ）。
2. 36件を1件ずつ見て、事故が起きたと思う候補を選ぶ。
3. 「CSVを保存」で `judgments_v2.csv` を保存し、`data/work/M2/review/judgments_v2.csv` に置く。
4. 指示役が、選んだ候補と重み最大の候補の一致率と、誤りの傾向を集計し、この報告に追記する。

生成：`data/work/M2/scripts/make_review_v2.py --review-only --keep-ids`。前の版は `index_v1.html`（200件・旧形式）、`index.before_twin_v2.html`（56件・双子の修正前）、`index.56items.html`（56件・双子の修正後）。

## 6. 追記：上下線の双子を多対多にした（2026-11-03）

`feat/routing-m1` の「双子の多対多化」（`jp-topology-2`、`docs/routing-reports/M1.md` 6章）を `feat/routing-m2b` にマージし、`accident-snap` を合わせた。規則の版は `jp-assign-2`。2章・3章の数値と、3章の項目3・6は、この章で置き換わる（旧版の `assignment.bin` は `assignment.v1.bin`、集計は `assignment.v1.audit.json`）。

変更点：

- 候補の組：候補の辺のうち、双子でつながるもの（連結成分）を1つの組にする。以前は、双子1本との2本だけを組にしていたので、反対側が短い辺に分かれていると、分かれた辺が別の候補として重みを奪っていた。組のスコアは辺のスコアの和、重みは組の代表（距離の近い辺）に載せる。
- `MIRROR`：載せた辺の双子のうち、事故の座標を折れ線に投影した点が辺の端の外にはみ出さないものを優先し、その中で距離が近い1本（同じなら辺番号が小さい方）に写す。端の内側に投影できる双子がなければ、距離がもっとも近い1本。写しは、載せた辺1つにつき多くても1本で、同じ事故を反対側の複数の辺に重ねて数えない。
- 幅員の判定（2本の `lanes` の和）：同じ規則で、事故の位置に対応する双子1本を使う。
- 検査（`verify_assignment`）：写しの元は「双子の関係にある、同じ重みの載せた辺」。双子に写し先がなければならない（複数の双子のうち1本以上に写しがある）。写しは載せた辺より多くない。
- 確認用の抽出：`review_sample.json` の辺に `twins`（双子の列）と、捨てた候補の `group`（組の代表の辺）を足した。以前の `twin`（1本）はなくなった。

道路種別ごとの「最大の重み0.8以上」：国道79.0%→85.3%、主要地方道78.6%→82.8%、一般県道81.8%→83.6%、市町村道82.0%→82.4%、高速・自専道80.9%→88.2%。国道の `ref` の一致率は変わらない（辺で97.2%、番号を持つ辺で98.8%、国道の事故全体で66.3%→66.2%）。

高速・自専道のコードの事故で残る「双子もMIRRORもない」964件は、60m以内に同じ路線の逆向きの辺がない区間（上下線が60m以上離れた山間部など）と、上下線で `ref`・`name` が違う区間（阪神高速の一部など）。出入口（motorway_link）は、ref・nameがない辺が大半で、判定の対象外（4,536件）。詳しくは `data/work/M2/review/auto_checks.md`。

確認ページ（`data/work/M2/review/index.html`）は、同じ56件（事故IDと区分は同じ）を新しい割り当てで作り直した。`make_review_v2.py --keep-ids` で前のページの事故IDを引き継いだ。

- 候補の組み方が変わったので、56件のうち15件で、候補の数・並び（番号）が変わった。残り41件は同じ。番号は、事故IDと候補の集合から決まるので、集合が同じなら変わらない。
- ページの保存の鍵が、`assignment.bin` のSHA-256の先頭16文字から作られるため、新しいページは前のページの回答を読み込まない（前の回答は、前のページを同じブラウザで開けば残っている。前のページは `index.before_twin_v2.html`）。前のページで回答を始めていれば、続きは前のページで行うか、新しいページでやり直す。
- 新しい割り当てで「要確認」の基準を当てると、4件（事故ID 27755・237634・1121993・1757974）は基準を外れた（最大の重みが0.8以上になった）。区分は前のページのまま残した。
