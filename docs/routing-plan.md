# 事故リスクを考慮した自前経路探索の計画書（案）

2026-11-03時点の計画案。`plan1.md`・`plan2.md` の比較と、その後の検討（SPF・交通量による正規化、交通量の欠損、LTS）をまとめたもの。12章の決定事項は、2026-11-03の利用者との一問一答で確認した。それ以外の内容は、利用者との合意がまだ取れていない。確定した仕様の正本は、引き続き `spec-decisions.md` と `route-scoring-decision.md` である。

記号の意味：
- 【実測】：`plan2.md` の作成時に、手元の全国OSM PBFと事故原本を集計した値
- 【推定】：前提を添えた見積もり
- 【要検証】：実装の前後に測る必要がある点

## 1. 背景：現行方式の問題

現行（`route-scoring-decision.md`）は、OSRMが返す数本の候補経路について、経路から72m以内の事故をガウス重み（σ=24m）×天候倍率×`10×死者+負傷者` で合計し、最小の候補を選ぶ。

構造的な問題は3つある。

1. **並行する別の道路の事故を数える。** 円で数えるため、高架の下の一般道や隣の幹線の事故が混ざる。
2. **候補がOSRM任せ。** リスクの低い経路を自分で探していない。公共OSRMのレート制限にも縛られる。
3. **偶然の変動に弱い。** 死亡事故が1件あるだけでスコアが10増える。事故0件の区間を完全に安全と扱う。

現行方式の根拠も弱い。徒歩57 ODの小規模実験1回で、地域は東京都心だけ。分割1では従来方式と差がなかった。時間帯・曜日・天候の条件付きでは検証していない。

## 3. グラフ構築

### 3.1 規模とメモリ

- 全国の共通グラフは約1,476万ノード・2,003万辺・有向辺4,005万【実測】。
- 常駐メモリは約1.25〜1.3GB【推定】。手段別に3つ作ると2.64GBになるので、共通グラフにする。
- 前処理はPBF 2パスで11秒【実測】。全体で10〜15分の見込み【推定】。

### 3.2 手段別の通行可否

| 手段 | 通行可とする条件（簡易規則） |
|---|---|
| 自動車 | motorway〜service、road。`access=no/private`、`motor_vehicle=no` は除外 |
| 自転車 | 一般道路、cycleway、track、path。footway・pedestrianは `bicycle=yes` のときだけ。motorwayと `motorroad=yes` は除外 |
| 徒歩 | 一般道路、footway、pedestrian、path、steps、track、cycleway。motorwayと `motorroad=yes` は除外 |

タグがないことを「禁止なし」や「安全」と同じに扱わない。日本向けの既定規則には版番号を付けて管理する。

### 3.3 辺の分割

- 辺は、交差点（共通グラフで次数が2でないノード）とwayの端点で区切る。形状だけを表す中間ノードはポリラインに残す。
- 事故には辺上の位置（始点からの距離）を持たせる。出発地や目的地がある辺を途中まで通るときに正しく数えられるようにするため。高リスク区間の切り出し（11.2節）にもこの位置を使う。
- 上下線が分かれた道路は「双子」として対応付け、2本に同じリスクを持たせる（当事者の進行方向は分からないため）。
- 小さな連結成分は、出発地・目的地の吸着先から除く。

### 3.4 一方通行・右左折禁止・ターンコスト

- 一方通行：辺に手段×方向の通行フラグを持たせる。自転車は `oneway:bicycle` を優先する。
- 右左折禁止：relation 28,005件【実測】。全国グラフはノードベースのままにし、**部分グラフ上の探索だけ「直前の辺」を状態に持つ**。via-way型も、小さな有限状態として扱う。
- ターンコスト：信号のあるノード（205,755件【実測】）の通過ペナルティと、角度に応じた右左折コストを付ける。左側通行なので、右折を重くする。
- 右左折禁止とターンコストは、コストを増やす方向にしか働かない。そのため、ノードベースで切り出した楕円は常に安全な枝刈りになる。
- 日本のOSMは一方通行タグの付与率が低い可能性がある【要検証】。リスクを避ける経路は細い道に入りやすいので、逆走経路を出していないかを、実装の早い段階で全国のODで確認する（9.4節）。

### 3.5 所要時間

- 自動車：`maxspeed` の付与率は3.3%【実測】。道路種別ごとの既定速度＋信号ペナルティで計算する。既定速度は、OSRMの所要時間に回帰して合わせる。
- 徒歩：80m/分。階段にはペナルティを付ける。
- 自転車：15km/h程度（仮定）。
- 時間は固定小数点の整数（秒）で計算し、分に丸めた値で上限を判定しない。

## 4. 事故の割り当て

### 4.1 方針

- まず、物理的な車道網（車道の辺と交差点クラスタ）に割り当てる。
- 1件の事故の重みの合計を1以下にし、並行する道路での二重計上をなくす。情報が弱い事故は、無理に割り当てず「帰属不明」として残す。
- 歩道（`footway=sidewalk`）は、親の車道のリスク密度を引き継ぐ。横断歩道は交差点クラスタに含める。公園内の通路など親のない辺に、周囲の車道の事故を漏らさない。

### 4.2 手がかり

現行の `data/app/accidents.csv.gz` にはない列を、原本から取り直す。

| 属性 | 分布【実測、2024年】 | 使い方 |
|---|---|---|
| 路線コード | 市町村道44.3%、国道20.7%、主要地方道16.8%、一般県道10.8%、高速・自専道2.2% | 高速・自専道かどうかは必ず一致させる。国道は番号とOSMの `ref` を照合する（trunkの `ref` 付与率はほぼ100%） |
| 道路形状 | 交差点43.4%、交差点付近14.8%、単路36.9%、一般交通の場所4.9% | 交差点の事故は交差点クラスタへ。トンネル・橋は立体交差の判別に使う |
| 車道幅員 | 単路6区分、交差点は組み合わせ | 候補の辺・交差点との整合を見る |

### 4.3 割り当ての手順

1. 35m以内の車道の辺を候補にする。高速・自専道のコードと、motorway・motorroadの一致を必須条件にする。
2. 交差点の事故は、30m以内の交差点クラスタ（20m程度以内の短い辺でつながる交差点ノードの集まり）に割り当てる。
3. 単路の事故は、次の積をスコアにして正規化し、0.1以上の候補（最大3本）に配分する。
   - 距離のガウス：σ = √(σ0² + 半幅²)、σ0は3〜4m【推定】
   - 路線区分×OSM種別の尤度（候補が1本しかない事故から推定した混同表）
   - 国道番号と `ref` の一致
   - 幅員・橋・トンネル・layerとの整合
4. 候補がない事故は「帰属不明」として、理由別に件数を記録する。

### 4.4 交差点のリスク

交差点クラスタのリスクは、**クラスタに外から入る辺**に載せる。どの経路も通過時にちょうど1回だけ加算されるので、辺の重みとしてDijkstraで扱える。進行方向が分からないので、右左折ごとの差は付けない。

### 4.5 N13

位置の標準偏差が25mあり、都市部では対応付けが曖昧になる。経路探索の土台が動いた後に、幅員区分と階層順の補助属性として追加する。OSMの形状は動かさない。

### 4.6 割り当ての検証

道路種別・道路形状で層別に約200件を抽出し、航空写真で人手判定して正解率を測る。帰属不明の割合も種別ごとに記録する。

## 5. リスクの定義

### 5.1 基本形：交通量なしのSPF＋経験ベイズ

道路種別 k（highway × 車線・幅員帯 × 人口集中地区か）ごとに、基準の事故密度 R[m][k][C] を推定する。これが、交通量を説明変数に持たないSPFに当たる。

```text
辺 e：
  μ_e    = T · ℓ_e · R[m][k][C]                   // 種別から見た期待件数（T=学習年数、ℓ=長さ）
  n_e    = Σ a_i                                  // 辺に割り当てた条件 C の事故の重み
  W_k    = T·R[m][k][C] / (T·R[m][k][C] + a_k)     // 長さによらない縮小の重み
  ŷ_e    = (1 − W_k)·μ_e + W_k·n_e
  risk_e = c_k · S[m][k][C] · ŷ_e · (天候の項)     // c_k は自動車の生活道路の係数（5.5節）。それ以外は1

交差点クラスタ v（最上位の道路種別 × 枝数 × 信号の有無）：
  ŷ_v = (1 − W_v)·μ_v + W_v·n_v,   W_v = μ_v / (μ_v + α_j)
```

- ガンマ分布の形状母数を長さに比例させる（α_e = a_k·ℓ_e）。こうすると、**辺を分割しても合計のリスクが変わらない**。
- 事故0件の区間も、種別の事前分布から正のリスクを持つ。
- 平均密度（リスク÷距離）を目的関数にしない。低密度の区間を足すだけで平均が下がってしまうため。
- a_k・α_j は、2019〜2022年で学習し、2023年で検証して決める。
- 本番のモデルは、評価が終わった後に2019〜2025年の全期間で学習し直す。

### 5.2 深刻度

- 件数は辺単位、深刻度は種別単位の平均 S（手段×種別×時間帯）に分ける。辺ごとに死亡事故1件の偶然に振り回されないようにするため。
- 死者10・負傷者1の重みは、現行の値を引き継ぐ。
- **加工済みデータの死者数・負傷者数は、事故全体の人数である。** 選んだ手段の当事者の被害ではない。表示では「その手段が関与した事故の被害指標」として扱う（`app/codebook_notes.md`）。

### 5.3 条件（時間帯×曜日区分）

- 基本の単位は、時間帯5区分×曜日2区分の10セル。「すべて」は該当するセルの件数と観測時間を合算して推定する。率を単純に足さない。
- `app/common.py:17` は今4区分なので、原本の日時から5区分で作り直す。
- 休日の判定と観測日数の分母には、同じ版の祝日表を使う。

### 5.4 天候

```text
ρ_e   = (n_e^w + β·ρ_k(C,w)) / (n_e + β)   // 天候が一致する割合を、種別の割合へ縮める
天候の項 = 1 + (M − 1)·ρ_e                 // M は現行の倍率を引き継ぐ（雨2、霧・雪4）
```

これは雨の日の事故確率ではなく、雨天の事故を重視する重み付けである。雨が降った時間（曝露量）は分からない。

### 5.5 自動車の生活道路の係数

> **2026-11-04 変更（M5、利用者の承認）**：この節の係数 c と折れ目の規則は、道路区分ごとの事故率による補正（曝露の補正）に置き換えた。詳細は `docs/routing-exposure-plan.md`、結果は `docs/routing-reports/M5.md`。
>
> - 自動車のリスクに、自専道・幹線・生活の3区分ごとの係数 f を掛ける。f_区分 = T_幹線 / T_区分、T_区分 =（区分の事故件数 / 区分の延長）/ 区分の事故率。事故率は H27 の走行台キロあたりの値（自専道9、幹線62、生活142件/億台km）、延長は国交省の道路統計、区分は警察の路線コードで分ける。件数は学習期間の事故で数える。
> - 辺には辺の group の区分の係数（group 0 が自専道、1〜3 が幹線、4〜10 が生活）、交差点クラスタには最上位の道路の group の係数を掛ける。所要時間には掛けない。徒歩・自転車には掛けない。表示する `weighted_risk` にも含める（下の既存の決定のまま）。
> - 本番（2019〜2025年）の値：自専道 0.246、幹線 1、生活 14.85。`risk.bin` の `c` は1.0のまま。
> - 置き換えた理由：c ∈ {1〜6} ではほとんど効かず（x は+44→+41ポイント）、範囲を100まで広げても折れ目が範囲によって変わった（1〜6では c=2、1〜100では c=20）。c の掃引の結果は M5.md の付録A。
>
> 以下は置き換える前の記述である。

件数でリスクを測ると、交通量の多い幹線道路は件数も多くなる。そのため、件数の少ない生活道路へ迂回しやすい。自動車の経路に限り、生活道路（OSMの `residential`、`unclassified`、`living_street`、`service`）のリスクに係数 c（1以上）を掛けて、この誘導を抑える。

- 係数は所要時間には加えない。表示の所要時間と遠回り上限が壊れるため。
- 係数は、表示する `weighted_risk` にも含める。選定に使う値と画面の値を同じにするため（既存の決定）。
- 徒歩・自転車には適用しない。

係数 c の決め方（2026-11-03決定：許容する増加幅は決めず、実験で決める）：

1. 係数を調整するデータ（2019〜2022年で学習、2023年で検証、9.3節の4地域の自動車のOD）で、c∈{1, 1.5, 2, 3, 4, 6} のそれぞれについて次の2つを測る。
   - x：事故考慮経路の生活道路を走る距離の割合が、最短経路と比べて何ポイント増えるか（ODの平均）
   - y：最短時間経路に対する将来事故の削減率（Y1〜Y3の平均）
2. 点 (x, y) を c の順に結んだ曲線で、両端（c=1 と c=6）を結ぶ直線から最も遠い点（曲線の折れ目）の c を採用する。生活道路への誘導を最も効率よく減らし、それ以上 c を上げても削減率が落ちるだけになる点にあたる。
3. c=6 でも x が0以下にならない場合は、グリッドを広げて測り直す。

注意：将来事故の件数も交通量で補正していないので、生活道路を通ることの害は y に表れない。そのため、c を「y が最大になる点」で決めることはできない。折れ目で決めるのは、この限界を踏まえた機械的な規則である。

### 5.6 徒歩・自転車

- 5.1節の件数ベースの経験ベイズのまま扱う。交通量による正規化は行わない。
- 既知の弱点：歩行者や自転車が多い道ほど件数が多く出るので、商店街や駅前を避けて、歩道のない裏道へ誘導するおそれがある。歩行者・自転車の通行量のデータがないので、根本的には解決できない。9章の評価で、この傾向の有無を確認する。
- LTS（Level of Traffic Stress）は採用しない（2026-11-03）。理由は次の2つ。
  - ストレスや快適さの指標で、事故リスクの推定モデルではない。
  - 判定に必要な制限速度や車線数の付与率が、日本のOSMでは低い（`maxspeed` 3.3%、`lanes` 7.2%【実測】）。道路種別から補うと、今の種別 k の言い換えになる。

### 5.7 将来の拡張：交通量による正規化（今回の範囲外）

自動車について、SPFに交通量を説明変数として入れ、`r_e = λ̂_e / (365 · AADT_e)` のように通過あたりに正規化する方法がある。今回の範囲には入れない。将来入れる場合の方針だけ記録しておく。

| 道路 | 交通量の扱い |
|---|---|
| センサスで観測がある区間 | 観測値を使う |
| 国道・県道で観測がない区間 | 道路種別・車線数・都市部か郊外かのグループ中央値で補う（補間） |
| 市町村道 | 外挿しない。5.5節の係数で扱う。幹線の値を借りると交通量を多めに見積もり、生活道路のリスクが過小になって、正規化の目的と逆になるため |
| 徒歩・自転車 | 正規化しない。車の交通量は、歩行者・自転車の曝露量ではない |

M5で、区分ごとの事故率（国交省の走行台キロあたりの値）による補正を入れた（5.5節）。区分の中の区間ごとの交通量の違いは扱っていない。この節の区間ごとの正規化は、引き続き今回の範囲外である。

前提の作業として、センサスとOSMの対応付けが必要になる。センサスの箇所別基本表には座標列がない【確認済み】。路線番号・区間延長・接続路線の連鎖でたどる必要がある。区間の線形データが別に公開されているかは【要検証】。

## 6. 探索

### 6.1 問題の定義

```text
T0 = 最短時間経路の所要時間
B  = T0 + D                         // D は許容時間。手動は 60 · max_detour_min（0〜30分）、
                                     // 自動は clamp(0.3 · T0, 3分, 30分)（behavior.md 4章「許容時間」）
min_P  R(P)   subject to  T(P) ≤ B
```

時間とリスクは別々に保持する。リスクを「遅い道路」に見せかけると、表示の所要時間と遠回り上限が壊れる。

### 6.2 手順

1. **最短時間経路** p0 を双方向A*で求める。
2. **楕円の切り出し**：始点からの時間と終点までの時間の和がB以下の辺だけを残し、局所番号の部分グラフ H を作る。確定ノード数が上限を超えたら、6.4節の処理へ。
3. **LARAC**：H 上で「時間＋λ×リスク」のDijkstraを、λを更新しながら5〜10回実行する。上限を満たす最良解 pd と、最適リスクの下界 lb を得る。
4. **部分グラフ上の時間予算付きRCSP**：pd を暫定解、lb を下界として、H 上で時間とリスクの多ラベル探索を行う。時間予算かメモリ上限に達したら、その時点の最良解を返す。完了すれば、このグラフとモデルの範囲で最適になる。
   - LARACだけで終わらせない理由：重み付き和では、凸包の内側にある制約内の最適解を必ず取りこぼす（`plan1.md` 1.3節の3経路の例）。
   - 全国グラフで直接ラベル探索すると応答時間が読めないが、H は小さいので現実的に回せる。
5. **候補の整理**（6.3節）。すべての候補について、最後に「所要時間 ≤ B」を検証する。

```text
fn route(req):
  risk = RiskView(req.mode, cells(req.period, req.day_type), req.weather)
  s, t = snap_to_edge(req.origin, req.mode), snap_to_edge(req.dest, req.mode)
  p0 = bidir_astar(G, s, t, w = time)
  B  = p0.time + req.max_detour_s
  H  = ellipse_subgraph(G, s, t, B)                // 上限超過なら reduced_ellipse（6.4節）
  pc = dijkstra(H, w = risk + EPS*time)            // リスク最小
  if pc.time <= B: return finalize([p0, pc])
  (pd, lb, hull) = larac(H, p0, pc, B, iters = 10)
  best = bounded_rcsp(H, B, incumbent = pd, lower = lb, budget = req.deadline)
  cands = dedup([p0, best.path] + feasible(hull) + penalty_alternatives(H, best.path, B, k = 2))
  assert all(c.time <= B for c in cands)
  log(best.status, best.gap)                       // optimal / bounded。利用者には出さない
  return finalize(cands[:6])
```

### 6.3 返す候補

| 候補 | 作り方 |
|---|---|
| 最短時間経路 | p0 |
| 事故考慮経路 | 上限の範囲でリスク最小の経路（現行仕様と同じ意味） |
| 代替経路 | LARACの途中解のうち上限を満たすもの。足りなければペナルティ法（事故考慮経路の辺を1.3〜1.5倍にして解き直す） |
| 重複の除去 | 共有する物理区間の長さが80%を超えるものは捨てる |

- 上限は6本（契約とフロントの上限）。重複除去で残った分だけ返し、6本に満たなくても無理に増やさない。自前探索の途中解は似た経路になりやすいので、2〜4本になることが多いと予想する【推定】。
- 「1分あたりの削減率が最大の点」（バランス案）が凸包上にあれば、代替経路の1本として含める。フロントを変えないので、バランス案というラベルは付けない。

### 6.4 探索範囲が大きすぎる場合

API仕様では、出発地と目的地の直線距離は30km以下である（`behavior.md:125`）。100km級の経路はないが、自動車の30km・遠回り上限30分では、楕円が大きくなり得る。

1. 確定ノード数が上限（初期値300万、実測で調整）を超えたら、出発地と目的地から3km以内を除き、tertiary以上の道路だけで楕円を作り直す。
2. それでも超えたら、最短時間経路とそのリスクだけを返す。

どちらの場合も、利用者には警告を出さず、ログにだけ記録する。

## 7. 性能

### 7.1 応答時間【推定】

前提：Rustの二分ヒープのDijkstraで、1コアあたり毎秒200万〜500万ノードを確定できる【要検証】。

## 9. 評価

### 9.1 目的

自前の経路探索にすること自体に意味があるので、**新方式を採用するかどうかの基準は設けない**（2026-11-03決定）。評価は次の2つに使う。

- 係数の調整（σ0、尤度表、a_k、β、生活道路の係数 c、高リスク区間のしきい値）
- 現行方式との比較の報告

### 9.2 データの分割

- 係数は、2019〜2022年で学習して2023年で検証するだけで決める。
- 比較の報告は、2019〜2023年で学習して2024〜2025年で評価する。これを1回だけ行う。
- 東京23区には、現行のσ=24mを決めた過去の実験の領域（東京都心）が含まれる。その領域と期間では現行方式が答えを見て調整されているので、比較は現行方式に有利に偏り得る。23区は除外せず、この偏りを報告に注記する。当時の領域の正確な範囲を記録したレポートは、すでに残っていない。

### 9.3 リスクの評価

- **地域**：東京23区、千葉市、さいたま市、横浜市の4地域。
- **OD**：事故の位置に依存しない点（人口密度で重み付けした道路ノード）から、手段別の距離帯で抽出する（徒歩0.5〜3km、自転車1〜8km、自動車2〜30km）。目安は、1地域・1手段あたり約100 OD（1手段あたり約400 OD）。
- **比較**：同じOD・条件・遠回り上限で、現行方式（OSRM候補＋ガウス）と新方式がそれぞれ経路を選び、評価期間の事故の多さを比べる。所要時間は共通の時間モデルで測り直す。
- **方式に依存しない物差し**を複数使う。
  - Y1：経路から15m以内の将来事故（範囲で数える方式に有利）
  - Y2：過去の実験のマップマッチング
  - Y3：4章の割り当てで、通過した辺・交差点に載る将来事故（新方式に有利）
- **指標**：
  - 最短時間経路に対する将来事故の削減率
  - 勝率（符号検定）
  - 追加の所要時間
  - 遠回り上限 Δ∈{0, 2, 5, 10, 15}分ごとの「削減率と追加時間の曲線」
  - 生活道路を走る距離の割合（自動車は5.5節の係数の調整に使う。徒歩・自転車は5.6節の弱点の確認に使う）
- **比較対象**：距離だけ、上限内でのランダム選択、現行方式。
- **要素を外した比較**：属性を使わない割り当て、交差点クラスタなし、経験ベイズなし、深刻度を辺単位にした場合、LARACだけ（RCSPなし）。
- **較正**：予測リスクを10分位に分け、評価期間の実績と比べる。
- 同じODの条件違いは、独立な標本として数えない。信頼区間は、地域と道路の共有を考慮したクラスターブートストラップで求める。
- 評価地域が関東の都市部だけなので、農村・山間部・積雪地での経路の質と、雪の倍率（4倍）の効果は確かめない。
- **M5での実施（2026-11-05）**：結果は `docs/routing-reports/M5.md`。計画との違いは次のとおり。
  - OD は人口のデータがないので、地域内の道路ノード（motorway を除く）から一様に抽出した。
  - Y2 は過去の実験のマップマッチングが残っていないので、距離だけで最寄りの辺に割り当てた将来事故で代用した。主な物差しは Y1〜Y3 の平均 Y とした（自動車は下の Yx を優先する。2026-11-05 の利用者の判断）。
  - 自動車では、事故1件ごとに道路区分の係数（5.5節）で重みを付けた Yx も出した。国交省の区分別の事故率を交通量の代わりとして正しいと認め、自動車の主な物差しは Yx とする（2026-11-05）。
  - 信頼区間は、OD 単位（地域で層別）と地域単位の2通りのクラスターブートストラップで求めた。
  - 較正は、深刻度・天候・係数を掛けない推定件数（`expected-count`）で行った。

### 9.4 全国での動作確認

配備は全国なので、全国からランダムに選んだOD（手段ごとに数百）で、リスク以外の項目を確認する。

- 経路の合法性：逆走、禁止された右左折、通行できない道路、不自然な吸着。一方通行タグの抜けは、地方ほど出やすいと予想する。
- 応答時間の中央値と95%点、ピークメモリ、6.4節の処理に入った割合。

OSRMは、所要時間の校正と、評価で現行方式を再現するための比較用に残す。

## 11. API応答への対応（フロントは変更しない）

フロントは変更しない（2026-11-03決定）。バックエンドの作業の後に変える項目は、Issue #26 にまとめた。既存の契約（`docs/api/openapi.yaml`）とフロントの応答検証（`frontend/src/api/validate.ts`）を満たす範囲で、新方式の値を返す。

### 11.1 候補ごとの値

| 項目 | 新方式で返す値 |
|---|---|
| 事故の集合B | 次の2つの和集合。(1) 経路の辺・交差点クラスタへの割り当て重みが0.1以上の事故、(2) 経路から72m以内にある帰属不明の事故 |
| `accident_count`、`fatal_accidents`、`injury_accidents`、`deaths`、`injuries` | 集合Bの観測件数・人数。割り当て重みが小数でも1件と数える |
| `weather_match` | 集合Bのうち、指定天候に一致する事故の集計（現行どおり） |
| `accident_points` | 集合Bから、現行の抽出規則（最大250点、死亡事故を優先）で選ぶ。帰属不明の事故も含む。フロントを変えないので、地図上で帰属不明の事故は区別されない |
| `weighted_risk` | 経路のモデルの値（5章のリスクの合計）。小数2桁。自動車は生活道路の係数を含み、選定に使う値と同じになる。帰属不明の事故はモデルに入らない |
| `risk_per_km`、`risk_reduction_percent` | 丸めた `weighted_risk` から計算する（現行どおり） |
| `within_detour` | 6.3節の検証により、全候補が真になる |

- 観測件数（`accident_count` など）とモデルの値（`weighted_risk`）を、別々の項目で返す。事故0件の経路でも、モデルの値は正になる。
- 候補は所要時間の昇順に並べ、IDを `route-1` から順に振る（フロントの検証条件）。
- 経路の長さと頂点数の上限（契約の80km・15,000頂点）は引き継ぐ。フロントの応答検証とナビの事前検査（`frontend/src/navigation/preflight.ts`）がこの値で検査しているため。最短時間経路が80kmを超えたら `route_too_long` を返し、それ以外の候補で80kmを超えるものは外す。頂点数が上限を超える場合は、表示用の形状だけを間引く。

### 11.2 高リスク区間

- 選ぶ基準は観測件数とする（案A）。
  - 経路を75mで分けた小線分（現行の契約の単位）ごとに、集合Bの事故の件数を数え、3件以上の小線分を高リスク区間にする。
  - 交差点クラスタに割り当てた事故は、クラスタの中心を経路に投影した点に置く。同じ交差点の事故が1つの小線分に入るので、「交差点で3件以上」もこの規則に含まれる。
  - 当初は「100mの窓で3件以上」としていたが、契約では区間の `severity_weight` が3以上でなければならず、窓に重なる小線分に3未満のものが出るため、小線分単位に改めた。
  - 3件にするか2件にするかは、実装後に典型的な経路で何区間出るかを数えて決める。2件にする場合は、契約の制約から「2件以上かつ深刻度の合計3以上」とする。
- `severity_weight` には、その区間の事故の `10×死者+負傷者` の合計を入れる。フロントは「深刻度の合計」として表示するため。
- 上限100件と `high_risk_total`、ナビ側の区間の構造（`segment_index`、元の頂点番号）は現行の契約どおり。区間を、経路ポリラインの小線分の範囲に対応付けて返す。

|---|---|
| `safest_id` | 6章の事故考慮経路。ただし、**全候補の `accident_count` が0のときは `null`**（現行の規則。フロントの検証条件でもある） |

### 12.2 未決事項

利用者の判断が必要な事項は残っていない。実装後に実測や実験で決めるとしていた次の3項目は、M5で決めた（2026-11-05、根拠は `docs/routing-reports/M5.md`）。

1. 生活道路の係数 c の値：c は道路区分ごとの事故率による補正に置き換えた（5.5節の冒頭）。本番の係数は自専道 0.246、幹線 1、生活 14.85（2019〜2025年の事故で計算）。`c` は1.0。
2. 高リスク区間のしきい値：**3件**。自動車の選定経路の区間数の中央値が、3件で10、2件で13になり（条件の指定なし）、2件では画面がさらに埋まる。徒歩・自転車はどちらでもほとんど変わらない。
3. 探索の時間予算：**RCSP 2,000ms、LARAC 10回、楕円 300,000ノード**（ラベル上限は2,000,000のまま）。自動車600組で、処理時間の99%点5.5秒、RCSP の完了率91.0%、縮小3.8%。
