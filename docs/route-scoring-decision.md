# 経路リスク集計方式の暫定決定

2026-10-24時点の暫定決定。根拠は小規模な時間分割実験1回で、証拠は弱い。本書の決定は統合時に `api/behavior.md` 6〜8章と `api/openapi.yaml` へ反映した。`spec-decisions.md` の「経路決定アルゴリズムは別途検証中」とされていた範囲を、本書で扱う。

## 1. 決定

候補経路ごとの事故リスクの集計を、現行の「経路から50m以内の事故を数えるハード判定」から、**距離で重み付けするガウシアン方式（σ=24m）** に暫定的に置き換える。

### 距離の重み

事故iの重みを、経路までの最短距離 `d` から次のように定める。

```text
w_dist(d) = exp(-d² / (2σ²))    σ = 24 m
d ≤ min(3σ, 100) = 72 m の事故だけを対象にする（72m超は重み0）
```

- `d` は、経路ポリラインを構成する線分までの最短距離。平面近似（局所正距円筒）は現行と同じ。
- 移動手段（walk/bike/car）による事故の絞り込みは現行どおり。実験では徒歩・自動車で同じ σ=24 を使った。σ は移動手段で分けない。分けるだけの根拠が実験で得られていない。

### 天候の重み（利用者指定）

利用者の指定により、事故に繋がりやすい天候だけに倍率を掛ける。

| 指定天候 | 一致する事故に掛ける倍率 |
|---|---|
| 雨 | 2倍 |
| 霧、雪 | 4倍 |
| 晴、曇、指定なし | 倍率なし（1倍） |

- 天候が一致しない事故は、除外せず1倍で評価に残す（`spec-decisions.md` の合意どおり）。
- 対象は雨・霧・雪。事故に繋がりやすい天候、という解釈による。
- 倍率の値は利用者の判断（勘）による暫定値で、実験では検証していない。後から調整できる。

### スコア

```text
S(route) = Σ  w_dist(d_i) × m_weather(i) × (10 × deaths_i + injuries_i)
```

- `m_weather(i)` は上の倍率。事故の天候が指定天候と一致するときだけ、倍率が掛かる。
- 事故の重み `10 × deaths + injuries` は現行どおり。

## 2. 決定の理由（距離の重みについて）

過去の事故だけから経路のスコアを計算し、将来の事故の多さと候補経路の順位が合うかで比べた（候補経路どうしのペアワイズ一致率）。

徒歩（57 OD、226経路）の分割2（2021-2023年で学習し、2024-2025年を予測）の結果は次のとおり。

| 手法 | 一致率 | 現行50mとの差（95%区間） |
|---|---|---|
| ハード50m（現行） | 0.719 | - |
| ハード75m | 0.747 | +0.028 [-0.019, +0.083] |
| **ガウス σ=24（本決定）** | **0.787** | **+0.069 [+0.021, +0.124]** |
| 線形減衰 R=80 | 0.762 | +0.044 [-0.003, +0.093] |
| マップマッチング T=50 | 0.728 | +0.009 [-0.070, +0.094] |
| 経路距離のみ | 0.438 | - |

- 評価の物差しは、検証期間の事故を経路から15m以内で数えたリスク（Y1）。
- ガウス σ=24 は、分割2のY1で現行50mとの差の区間が0を跨がなかった、選択パラメータのうち唯一の手法である。
- 距離のみ、ランダムより、どの集計法も明確に良かった。事故の集計には予測力がある。
- 自動車（30 OD）は、全手法が0.91〜0.97の範囲に集まり、手法間の差は区間が0を跨いだ。

## 3. 証拠の弱さ

この決定は、次の理由で確かなものではない。

1. **分割1では、ガウス σ=24 は現行50mと同等だった。** 一致率は0.731対0.734で、差は-0.003 [-0.030, +0.026]。分割1の点推定だけを比べると、ハード75m（0.753）のほうが上だった。
2. **差が確認できたのは、分割2のY1だけである。** 別の物差しY2（検証期間の事故をマップマッチングで数えたリスク）では、差は+0.058 [-0.013, +0.131]で、区間が0を跨いだ。
3. **多重比較の補正をしていない。** 多数の手法とパラメータを比べたうち、1つの区間が0を跨がなかったことは、偶然でも起こり得る。
4. **ガウスを選んだ最終判断は、分割2の結果を見たあとである。** 群ごとの最良パラメータは分割1で選んだが、手法の群をまたいだ選択は分割2を見て行った。
5. **検出力が足りない。** 区間は±0.08前後で、±0.05程度の差は見分けられない。
6. **範囲が狭い。** 東京都心の1領域だけの結果である。郊外や幹線道路の少ない地域は未検証。
7. **時間帯、曜日区分、天候の条件と倍率は、実験で使っていない。** 実験は移動手段による絞り込みだけで、条件を付けたときの動作と、天候の倍率の効果は未検証。

## 4. 実験で分かった、関連する事実

- 50m以内の事故のうち、徒歩で約61%、自動車で約50%は、経路が通る道路ではなく、別の道路上の事故だった。15m超の事故は94〜99%が別の道路上だった。「並行する別の道路の事故を拾う」という問題は実在する。
- 事故点は、OSMの道路中心線の近くにあった（最寄りリンクまでの距離は中央値1.9m、90%点5.9m）。座標の誤差は、想定より小さい。
- マップマッチングは、現行50mより優れているとは示せなかった。徒歩の経路の約18%が、主な車道のリンクに対応しなかった（歩道、公園、路地など）。
- 最もリスクの低い経路が、現行50mとマップマッチングで異なるODは、徒歩で21/57、自動車で5/30だった。集計方式によって、選ばれる経路はかなり変わる。

マップマッチングは、現時点では採用しない。道路データの自己ホスト、OSMの版管理、スナップ精度の検証の負担に見合う改善が、確認できていない。

## 7. API形式への反映（現行 `openapi.yaml` との差分）

統合時に、次を `openapi.yaml` へ反映した。

| 項目 | 現行 | 変更後 |
|---|---|---|
| `RouteCandidate.weighted_risk` | 整数（`deaths×10+injuries`） | 実数（小数2桁）。`w_dist × m_weather × (10×deaths+injuries)` の合計。指定天候により値が変わる |
| `RouteCandidate.risk_per_km` | `weighted_risk/max(距離km, 0.001)`、小数3桁 | 丸めた `weighted_risk` から計算（提案） |
| `RouteResponse.safest_id` | 必須の文字列 | 必須だが `null` を許す。全候補で事故が0件のとき `null` |
| `RouteResponse.extra_minutes` | 必須の数値 | `null` を許す。`safest_id` が `null` のとき `null` |
| `RouteResponse.risk_reduction_percent` | `null` を許す（基準リスクが0のとき） | 変更なし。`safest_id` が `null` のときも `null` |
| `RouteResponse.radius_m` | 50に固定 | 72に固定 |
| `RouteResponse.distance_weight_sigma_m` | なし | 新規。24に固定 |
| `RouteResponse.relaxed_conditions` | 解除した条件 | 常に空配列（`backend-spec.md`） |
| `RouteCandidate.exact_condition_count` | 緩和前の件数 | 非推奨の互換値（`backend-spec.md`） |
| `RouteCandidate.weather_match` | なし | 新規（`backend-spec.md`） |
| 高リスク区間の `weighted_risk` | 整数 | `severity_weight` に改名。値は `10×死者+負傷者` の合計（距離減衰と天候の倍率なし）。しきい値3を維持 |
| `warnings` | 条件緩和などを含む | 条件緩和は削除。事故0件の警告を維持 |

### 文面（確定）

`{N}`、`{d}`、`{x}`、`{y}` は、応答の値で置き換える。

| 項目 | 場面 | 文面 |
|---|---|---|
| `reason` | 通常 | 取得した{N}候補のうち、最短時間経路から+{d}分以内で、距離で重み付けしたリスクが最小の経路を選びました。追加{x}分、リスク{y}%減です。 |
| `reason` | 最短時間経路と同じ | 今回は最短時間経路が事故を考慮した経路と同じです。 |
| `reason` | 基準リスクが0 | 最短時間経路のリスクが0のため、削減率は算出できません。 |
| `reason` | 全候補で事故が0件 | 全候補で該当する過去の事故がないため、事故を考慮した経路は選んでいません。 |
| `risk_note` | 常に | 過去の事故件数に基づく参考指標です。経路から約72m以内の事故を、近いほど重く数えています。（雨・霧・雪の指定時のみ）雨・霧・雪を指定した場合は、同じ天候の事故をさらに重く数えます。交通量や通行回数で補正した事故確率ではありません。 |
| `warnings` | 全候補で事故が0件 | 該当する事故が0件でも、安全であることの証明ではありません。 |

- `risk_note` の天候の文は、指定天候が雨・霧・雪のときだけ入れる。
- 「通常」の `reason` は、候補が複数あり、最短時間経路と事故を考慮した経路が異なるときの文面である。

### 判定の補足

- 全候補で事故が0件かどうかは、事故の集合Bが空かどうかで判定する。`weighted_risk` を小数2桁に丸めても、Bが空でない候補は0.00にならない（打切り72mでの事故の重みは最小で約0.011で、深刻度は1以上のため）。
- 最短時間経路のスコアが0で、ほかの候補にB内の事故がある場合は、最短時間経路が `safest_id` になり、`risk_reduction_percent` は `null` になる（基準リスクが0）。これは現行の挙動と同じである。

## 8. 次に検討すること

実験の報告で挙げられた、検出力と範囲に関する課題である。

- OD数を増やして検出力を上げる。
- 郊外や幹線道路の少ない地域でも確かめる。
- 時間帯・曜日区分・天候の条件を付けたときの動作を確かめる。
- 距離減衰とマップマッチングを併用する案を試す。
- 交差点の事故を、接続する全リンクに按分する案を試す。
- 交通量で正規化して評価する（データの入手が前提）。
