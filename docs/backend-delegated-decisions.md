# API・前処理・運用の委任判断

2026-10-24、GPT-6.1 Solによる技術判断。これは**最終統合時の変更指示**であり、既存OpenAPIや実装を更新した記録ではない。利用者が具体的なフィールド名・ポート・上限値まで指定したという意味ではない。

最新の統合仕様は[backend-spec.md](backend-spec.md)にまとめた。本書は判断理由の記録として残し、追加合意と初期アクセス・提供元・共有制御は同仕様を優先する。

根拠の優先順は、[利用者との決定記録](spec-decisions.md)、利用者が確定扱いにした[PR #1の固定head](https://github.com/jphacks/tkb_2612/tree/ac64e525a758f47bdb61399827bd4619f79e968c/docs)、本書の委任判断。既存の[OpenAPI](api/openapi.yaml)・[挙動案](api/behavior.md)・[構成案](architecture.md)は比較材料として読んだ。`app/`・`backend/`・`frontend/`の実装は根拠にしない。PRのbaseは`3a2fd9b59a477323f6553c6709fd9a3dea5a3816`。

## 利用者確認済みの前提

- Rust/Axum、React/TypeScript/Vite/MapLibre GL JS。バックエンドはクラウド。クラウドと細かな技術判断は委任された。ハッカソンの限定利用で、一般ユーザー向け公開はしない。
- 徒歩・自転車・自動車、出発地/目的地、許容する遠回り、最短時間経路と事故履歴を考慮した経路の比較。経路決定アルゴリズムとフロントエンドの詳細は別途検証中。
- PR #1の5時間帯、平日/休日、Asia/Tokyo・分単位、条件の自動/手動、GET `/api/conditions`、Open-Meteo、丸めた地域座標、API 2.0/前処理スキーマ2の合意。
- **天候を除外条件にしない。** 時間帯・曜日区分・移動手段などの条件は維持し、全天候と指定天候一致の件数/死傷者数を分けて返す。0件もそのまま返し、条件を自動緩和しない。死傷者は該当事故全体の人数。
- 座標・日時の欠損/不正は行を除外して続行し、除外件数と理由を開発者向けに記録する。
- 経路・住所の外部提供元が送信座標/住所を運用ログへ保存することは許容する。提供元まで含めた完全な無保存は要求せず、自アプリの永続位置保存機能は追加しない。

## 6.1 Solに委任された技術判断：APIと集計の表現

| 項目 | 決定と根拠 |
|---|---|
| 正式API | POST `/api/route`、GET `/api/geocode`、GET `/api/conditions`、GET `/api/health`。PR #1のパス・条件取得契約を維持する。`/api/status`は同じhealth応答を返す非推奨エイリアスとして残す。 |
| 契約版 | 未リリースの統合契約を`api_version: "2.0"`として揃える。生成TS型・Rust DTO・fixtureを同時に更新し、旧デモの完全互換は要求しない。PR #1の互換入力は維持するが、旧デモを受け入れ試験の正本にしない。 |
| 入力 | 正規入力は`origin/dest={lat,lon}`、`mode=walk/bike/car`、`period/day_type/weather`は日本語または`all`。省略はPR #1の既定値（mode=walk、各条件=all、max_detour_min=10）。period/weatherの整数・null、`hour`・`時間帯`の互換入力と優先順はPR #1通りに入口だけで正規化する。day_typeは整数を受理しない。routeへ出発日時を追加しない。 |
| 型と検証 | JSON数値は有限のみ。数値文字列とboolを数値として受け入れない。整数型の値は12.0のような整数値表記も受理する。JSONオブジェクトの重複キー、既知GETパラメータの重複は400。未知キーは無視する。UTF-8のJSONと`application/json`を要求し、空/16,384バイト超の本文も400へ統一する。外部呼出し前に全入力を検証する。 |
| 座標と単位 | 入力の名前付きlat/lonと、GeoJSONの`[lon,lat]`を区別する。緯度20〜46/経度122〜154、標高なし。秒・メートル・分を既存フィールドの定義通り明記する。PR #1の直線距離20m〜30km、許容分0〜30、候補80km/15,000頂点は初期の受付・応答保護値として維持し、アルゴリズム側の接続検証で不足すれば共同で更新する。利用者がこれらの数値を指定したとは扱わない。 |
| 件数・人数 | 非負整数。内部加算はu64で行い、外部JSONではJavaScriptが正確に表せる範囲を検証する。無該当は0、配列は`[]`とし、値なし/nullと混同しない。 |

経路候補ごとに、移動手段・時間帯・曜日区分と、別途確定する経路周辺条件を適用した集合をBとする。天候ではBを減らさない。

- 既存の`accident_count / fatal_accidents / injury_accidents / deaths / injuries`は**B全体の全天候集計**にする。死亡事故数は死者1人以上、それ以外の該当人身事故を負傷事故数とし、両者の和を事故件数にする。死亡事故内の負傷者もinjuriesへ含める。
- 新規`weather_match`は必須フィールドとし、天候指定時は同じ5項目を持つオブジェクトで「Bのうち指定天候と一致する事故」だけを集計する。該当なしなら全項目0。天候が`all`なら`null`とし、一致条件を指定していないことを表す。これにより、0件と未指定を区別できる。
- `effective_conditions`には正規化した要求条件を返す。天候指定は一致集計/評価への指定を表し、全天候集計を除外したという意味にはしない。`relaxed_conditions`は移行上の混乱を避けるため**常に空配列**の互換フィールドとして残す。`exact_condition_count`は天候指定時の`weather_match.accident_count`、all時の`accident_count`と同値の非推奨フィールドにする。
- `weighted_risk`等の選定スコア、削減率、区間スコアは**件数/人数集計とは別**。旧`10×死者+負傷者`を採用済みの式と扱わず、式・係数・型の具体化はアルゴリズム側の結論を統合する。`weather_match`から選定スコアをフロントが再計算する契約にしない。
- 事故点はBから描画用に抽出する。GeoJSONと`day_type`を維持し、最大250点・死亡事故優先・元順の等間隔抽出を初期の表示量制限として採用する。間引きで集計を変えず、`points_shown`と配列長を一致させる。高リスク区間の選び方・スコア・閾値は別検証に従い、旧案の「3以上/100区間」等をここで確定しない。

## 6.1 Solに委任された技術判断：前処理とデータの失敗

- 2019〜2025の7原本を年昇順・入力行順で処理し、原本は変更しない。CSVの引用/改行、UTF-8 BOM/UTF-8/cp932を扱い、ヘッダは空白を正規化して名前で参照する。正規化後に必須列が重複した場合は失敗させる。旧案の「後勝ち」に依存して誤った列を読むことを避ける。
- 座標・日時の不正行除外は確認済み方針。人数・当事者・天候等の必須値についても、型/年度別コード表に適合しない行は補完せず除外し、`invalid_casualties / unknown_party_code / unknown_weather_code`等へ分ける。例外を一括で握りつぶさず、I/O・CSV構文・途中の復号失敗・欠損ファイル・欠損必須列・コード表不一致・全行除外は**前処理全体の失敗**にする。利用可能な一部年度だけを黙って公開しない。
- 年度別コード表で当事者A/Bのいずれかが該当すれば手段対象とする。歩行者61、自転車51/52、自動車の既存コード集合をPR #1の分類案に沿って照合し、二輪/原付/特定小型原付43を自転車へ混ぜない。対象手段のない`modes=0`行は保持して別計数する。これは分類の委任判断で、コード表照合前の正しさを主張しない。
- PR #1の17列gzip CSV（weather直後にday_type）、`schema_version=2`を使う。日時は事故発生暦日から判定し、source_yearと発生年を混同しない。DMSを十進度へ変換し、出力時だけ緯経度を小数7桁にする。道路へのスナップや真の事故IDを推測した重複行削除は追加しない。
- 内閣府祝日CSVを前処理とconditionsで共用・同梱し、取得元・ハッシュ・収録年を記録する。土日または祝日表にある日を休日とし、年末年始・お盆・企業休業日の追加特例は設けない。**元日や土日を平日扱いにしない**よう、PR #1の年末年始に関する曖昧な注記を置き換える。祝日表範囲外はPR通り土日だけで判定し、conditionsに`holiday_table_covered=false`、前処理metadataに該当行数を記録する。[内閣府の祝日表](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)
- 入力件数=保持件数+除外件数を検査する。複数の不正がある行は検査順で最初の理由へ1回だけ計上し、年度別・理由別件数を残す。読込・必須列→座標→日時→人数→分類値の順を固定する。除外原本行をWebへ返さず、監査には年度・行番号・理由だけを使う。
- 成果物のgzipとmetadataは同じ不変releaseに置く。gzip全体のSHA-256を`dataset_id`、行順0始まりを事故IDとし、事故参照は両者の組。起動時にschema/hash/件数/必須値・列挙値を再検証する。16列デモ成果物は流用しない。起動ロード失敗はプロセス停止。準備途中をHTTP公開する場合だけhealth/routeで503 `data_unavailable`。データ更新は新イメージの全件ロード確認後に切り替え、旧イメージへ戻せるようにする。

## 6.1 Solに委任された技術判断：条件取得と外部通信

- conditionsの日時・座標入力、5種類の`weather_status`、現在±15分・予報・過去の分岐、5秒の気象通信/8秒の全体期限はPR #1を維持する。天候が取れなくても時間帯・曜日区分を200で返す。気象全体期限は、応答JSONを用意する余裕を含めてクライアントの10秒より短くする。
- WMO→5天候のPR #1対応表を、気象の自動初期値を作る**技術上の近似**として採用する。0/1/2→晴、3→曇、45/48→霧、霧雨/雨/雷雨→雨、雪系→雪。未知コードはunavailable。現場の事故天候判定と同じ精度を保証せず、自動値で手動入力を上書きしない。[Open-Meteoのコード表](https://open-meteo.com/en/docs)
- 気象は小数2桁へ丸めた地域座標だけを送る。PR #1のメモリ限定キャッシュ（成功応答、TTL600秒、最大1024地点）を採用し、永続化はしない。住所・経路のキャッシュは標準off。提供元がキャッシュ必須なら利用条件を満たす接続方式を選び、黙って位置保存を追加しない。
- route/geocodeの全体期限35秒、個別上流8秒、上流応答最大12,000,000バイト、提供元別待ち行列上限16を初期保護値にする。再試行は自動では行わない。CPU集計も期限/切断を確認して停止し、HTTP応答だけ終えて裏で走り続けない。上流の受付レート・同時数・日次上限は提供元単位で管理する。Cloud Run最大1台でも共有制御が不要とはしない。
- 住所検索はtrim後Unicode2〜200文字、qは1個、提供元順の先頭5件。空結果は200。ラベルをHTMLとして扱わない。住所提供元はGeoapifyを採用し、外部JSONを既存のlat/lon/labelへ正規化する。公開Nominatimへは接続しない。経路提供元は別検証の結論を設定で差し替え可能な境界へ接続し、徒歩/自転車を自動車プロファイルへ代替しない。詳細・公式根拠・制限値は[統合仕様](backend-spec.md)に記載する。

## 6.1 Solに委任された技術判断：HTTP・配備・検証

- APIエラーは`{"error":{"code":"…","message":"…"}}`。400入力不正、404未知API、405不正メソッド（Allow必須）、422経路上限、502経路なし/上流失敗、503未準備/混雑/全体期限、500内部失敗とする。上流429は502、conditionsの気象失敗だけは200のunavailable。アプリに到達する前のCloud Run 429/認証エラー等は同じJSON形式を保証できないため、クライアント側では非JSON失敗も扱う。
- APIの成功/失敗は`no-store`・`nosniff`。APIを静的配信より先に解決する。配信rootはビルド済みdistだけ、既知パス以外は404。HTML/manifest/SWは再検証、ハッシュ付きassetsはimmutable。原本・前処理成果物・ソース・dotfile・ディレクトリ一覧を配信しない。PWAの画面や操作は別検証とし、API/位置/経路/外部応答を永続キャッシュしない配信境界だけを採用する。
- 開発はAxum `127.0.0.1:8000`、Vite `127.0.0.1:5173`、strictPort、`/api`プロキシ。本番は同一オリジンでCloud RunのTLS終端を使い、Axumは`0.0.0.0:$PORT`（ローカル既定8080）で待受する。CORSは初期不要。パスは本番で絶対パスにし、上流URL・帰属・連絡先UAは設定値、秘密キーはサーバ専用secret参照、VITE変数には置かない。
- Cloud RunのCPU/RAM・ログ除外・終了後の停止と費用は[クラウド選定](cloud-selection.md)に従う。位置/住所/経路の永続保存機能を新設せず、アプリ/HTTPクライアント/プラットフォームのログも別々に確認する。外部提供元の保持はアプリ内無保存と同じ保証にしない。
- 初期実演はCloud Run IAMと開発者端末の認証付きlocalhostプロキシを使う（**その後、利用者決定によりCloud Run＋IAPでの直接アクセスへ変更。[backend-spec.md](backend-spec.md) 8章を優先**）。アプリ独自ログインは作らない。上流の全インスタンス共通制御はFirestoreの時刻/件数だけの運用状態で実装し、位置/検索語/経路は格納しない。これらは利用範囲と上流制限を満たすための委任判断である。
- 契約試験はOpenAPI 3.1の構文・参照、JSON SchemaとDTO/生成TSの一致、全天候/天候一致・0件・all/null・非緩和・5時間帯/祝日境界・不正入力時の上流0回・期限キャンセル・データ破損/原子切替を確認する。旧デモのテスト件数や数値をそのまま合格条件にせず、確定仕様からfixtureを作る。アルゴリズム結果の検証、実上流、スマートフォン、メモリ/起動/応答時間は別の受け入れ項目にする。

## 統合時の変更と残件

OpenAPI・behavior・architectureへ、PR #1の契約を先に取り込み、上記の全天候/天候一致、非緩和、前処理失敗、Cloud Run運用を同じ変更単位で反映する。自動緩和の例・試験と、旧スコア式の採用済み表現を除き、`weather_match`とそのnull条件をフロントの契約検証へ連携する。スコア/経路周辺条件/区間抽出はアルゴリズム側の結論で補う。

外部運用ログ許容は追加合意で解決済み。審査員各自端末を必須にしない初期実演方式は上記の委任判断で確定する。アカウント/予算、実測性能、提供元の利用条件、アクセス設定、共有制御、ログ除外の実効性は配備前の確認・検証残件であり、検証済みとは扱わない。経路/フロント側への依存は[統合仕様](backend-spec.md)へ分離した。
