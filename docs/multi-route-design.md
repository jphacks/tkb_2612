## 1. 結論

- **カードは最大3枚**：最短時間経路、中間案、事故考慮経路。中間案は、選ぶ意味のある差があるときだけ出す。出せないときは今の2枚のままにし、「中間案がない」ことは表示しない。
- **中間案は、許容時間の半分を上限にした探索で作る**（利用者の±50%案のうち0.5倍の部分）。1.5倍（許容時間を超える経路）は出さない。
- **中間案のラベルは追加時間**：「中間案（+4.0分）」とし、「バランス」「おすすめ」のような評価の言葉を付けない。並び順は時間の順で固定する。
- **中間案からもナビを開始できる**。選べるのに出発できない状態は作らない。
- **スマホは地図の下に縦3行の比較一覧**、PCは地図横の一覧。全候補一覧（最大6本）は今のまま残す。
- **作る前に2つ測る**（6章の1と3）：中間案が出る割合と、中間案と事故考慮経路の順序が評価期間の事故でも保たれるか。どちらかが否定的なら、3枚目は作らない。

## 2. 理由

### 2.1 利用者の困りごと

【事実】事故考慮経路は「最短時間＋許容時間以内で推定リスク最小」の1本である（`behavior.md` 8章）。利用者は、結果を見る前に許容時間を決めなければならない。「+3分ならどれだけ減るか」を知るには、許容時間を変えて検索し直すしかない。

【事実】RCSP は上限の中でリスクを最後まで減らそうとして、上限近くまで使う（M5.md 7.3節。LARAC だけの場合より追加時間が60〜80秒長く、削減率はほぼ同じ）。自動車の追加時間は最短時間の平均50%にあたる（M5.md 0.3節の4）。

### 2.2 中間案に価値がある根拠

【事実】遠回りの上限ごとの平均（M5.md 7.2節、評価期間の事故で測った削減率／追加時間）：

| 手段 | Δ5分 | Δ10分 | Δ5分で得られる割合 |
|---|---|---|---|
| 徒歩（Y） | 50.2%／+266秒 | 53.6%／+498秒 | 削減の94%を、追加時間の53%で |
| 自転車（Y） | 49.0%／+284秒 | 53.9%／+538秒 | 削減の91%を、追加時間の53%で |
| 自動車（Yx） | 56.9%／+284秒 | 60.7%／+551秒 | 削減の94%を、追加時間の52%で |
| 自動車（Y、参考） | 27.1%／+284秒 | 36.4%／+551秒 | 削減の74%を、追加時間の52%で |

許容時間が初期値の10分なら、5分を上限にした経路は、平均で削減のほとんどを半分の追加時間で得ている。これが「+5分の経路も見せる」価値の根拠である。

【推定】ただし平均の話で、OD ごとには中間案が事故考慮経路と同じになる場合も、差が小さい場合もある。出る割合は6章の1で測る。

### 2.3 中間案の作り方に0.5倍の探索を選ぶ理由

| 作り方 | 良い点 | 問題 |
|---|---|---|
| 既存の凸包上の解・代替経路から選ぶ（Opus、Astra） | 探索を増やさない | 凸包上の解は、時間の上限を小さくしたときの最適解とは限らない。80%の重複除去で消えることがある（`behavior.md` 5章「候補の整理」の3。必ず残るのは p0 と best だけ） |
| 1分あたりの削減率が最大の経路（Fable、`routing-plan.md` 6.3節） | 割の良い経路を直接拾える | 追加時間がごく小さい経路ほど比率が大きくなりやすく、利用者が望む折衷案と一致するとは限らない（Astra の指摘） |
| **許容時間の半分を上限にした探索（採用）** | どの経路を選んだか一文で説明できる。他より遅くてリスクも高い経路が混ざらない | 探索が1回増える（3.2節） |

### 2.4 許容時間の1.5倍を出さない理由

- 利用者が決めた上限を超える。「許容時間を超えます」と断っても、初期値10分を選んだ利用者に15分の経路を見せることになる。
- 楕円が広がり、楕円の上限（30万ノード）に当たりやすくなる。【事実】東京23区の自動車は、すでに10分で18.7%が縮小に回っている（M5.md 8.2節）。
- 【事実】M5.md 7.2節では、Δ10分からΔ15分に広げても削減は数ポイントしか増えない（徒歩53.6%→57.4%、自動車 Yx 60.7%→61.7%）。
- ナビ用データが4本分になる（4.2節の見積もりがさらに増える）。

「許容時間を広げたらどうなるか」は、利用者が許容時間を変えて検索し直せば分かる。許容時間の意味（遠回りの上限）は変えない。

## 3. 候補の作り方（バックエンド）

### 3.1 手順

`behavior.md` 5章（main 版）の手順5〜7で best が決まった後、手順8（候補の整理）の前に、次を足す。手順5で pc が B 以下になり、LARAC と RCSP を飛ばした場合も同じく行う。

1. 許容時間 T（分）が4分未満なら、中間案を作らない（上限が2分未満になり、事故考慮経路との差に意味がない）。T=0 は最短時間経路だけになる。
2. 上限 `Bm = T0 + 600 × floor(T/2)`（デシ秒）とする。分単位で切り捨てるので、T=10なら5分、T=15なら7分になる。
3. 全体のグラフから Bm で楕円を切り出し直し（`behavior.md` 5章の手順4）、手順5〜7と同じ探索を Bm で行う（pc が Bm 以下ならそれで終わる）。【事実】H（`Subgraph`）は `df`・`db` を持たないので、H の中で Bm に絞ることはできない（実装で確かめた）。切り出しが大きすぎれば同じ縮小を行い、それでも大きすぎれば中間案は作らない。RCSP の時間予算は本体と同じ2,000ms。
4. 得た経路を m とする。m が p0 または best と有向辺の列・吸着点まで同じなら、中間案はないものとする。
5. 候補の整理では、m を p0・best の次に置き、80%の重複除去の対象から外す（p0・best と同じく常に残す）。他の候補の重複判定では m と比べない。最大6本の上限には含める。

m を候補に足すと、`behavior.md` 8章の既存の選定にも効く。

- safest は丸めた `weighted_risk` の最小で、同点なら時間の短いほうを選ぶ。m が best と丸めた値で同点の場合や、best の RCSP が打ち切られて m のほうがリスクが低い場合は、m が safest になる。このとき4.1節の条件4を満たさないので `middle_id` は null になる。
- 「全候補で事故0件」の判定と、`reason` の `{N}`（候補数）には m も入る。

探索範囲を縮小した場合（`behavior.md` 5章「探索範囲が大きすぎる場合」の1）は、縮小後の H で同じことをする。候補が p0 だけの場合（同じく2）は作らない。

### 3.2 時間

【事実】決定値での `evaluate` の壁時計は、自動車の99%点8.2秒、最大12.7秒（M5.md 8.2節）。RCSP の時間予算は2,000ms。

【推定】中間案の探索は H の一部で行うので、1回目より速い。それでも最悪で LARAC 10回＋RCSP 2,000ms が加わり、自動車の最大は15秒前後になる見込み。35秒の期限には収まるが、6章の5で測る。中間案の RCSP の時間予算を1,000msに下げる選択肢もある（M5.md 6章では1,000msと2,000msの差は改善3組）。

### 3.3 RCSP が打ち切られた場合

RCSP が予算内に終わらなかった場合も、その時点の最良解を m とする。完了しても、モデルの範囲での最適にすぎない。そこで画面には追加時間だけを書き、「+5分以内で最小」とは書かない。2.3節の「一文で説明できる」は、開発者や仕様書に向けた説明である。完了したかどうかは内部の記録にだけ残す（`behavior.md` 5章と同じ）。

## 4. 中間案を出す条件と、ナビ

### 4.1 カードにする条件（バックエンドで判定）

次をすべて満たすとき、`middle_id` に m の ID を入れる。満たさなければ `middle_id=null` とし、m が fastest・safest のどちらでもなければ m を候補から取り除く（m は重複除去を免れて入っているので、灰色の代替経路として残さない。取り除けば、6本の枠で押し出された候補を除いて、m のない場合と同じ候補になる）。

1. `safest_id` が null でなく、safest が fastest と別の経路である。
2. 全候補の事故が0件の場面ではない。【事実】Issue #26 項目5で、新方式はこの場面でも事故考慮経路を選ぶようになる。徒歩56%・自転車41%がこの場面である（M5.md 8.3節）。根拠の弱い差をさらに細かく見せないため、ここでは中間案を出さない。
3. 最短時間経路のリスクが正で、削減率を計算できる。
4. 時間とリスクが、fastest と safest のあいだにある：`fastest.duration < m.duration < safest.duration` かつ `safest.weighted_risk < m.weighted_risk < fastest.weighted_risk`（丸めた値で比べる）。
5. 差に意味がある（しきい値は**仮置き**。6章の1・3の結果で決める）：
   - m の追加時間が、safest の追加時間より1分以上短い。
   - m の削減率が、safest の削減率の半分以上。

条件5の値は仮置きである。実測（6.1節）では、条件2を除いて81〜90%の検索で中間案が出た。K を0.7にしても74〜87%で、0.9にすると約45%に下がる。値は利用者が決める。

### 4.2 ナビ

- 中間案からも開始できる。ナビ用データは `fastest_id`・`safest_id`・`middle_id` の経路に付ける（同じ ID なら1経路分）。
- 【事実】ナビ用データは、ガイダンスを含めて1経路あたり最大 3,383,612 バイト、2経路で 6,767,224 バイト。検証用の上限は6,800,000バイト、応答全体の小計は約12.65MB、負荷試験の基準は非圧縮12,000,000バイト（`behavior.md` 7章「ナビデータの件数と応答サイズ」）。上限を超えると500になる。
- 3経路にすると、ナビ用データは最大 10,150,836 バイト、応答全体の小計は約16.03MB になる。必要な改定は2つ：
  - ナビ用データの検証用の上限：6,800,000 → 10,200,000 バイト。
  - 負荷試験の基準：12,000,000 → 16,100,000 バイト。
  - 【実装後】main（#22 の案内）との統合で、この2つの改定を反映した（`behavior.md` 7章）。
- 【事実】クライアントの期限180秒は、下り1Mbpsで非圧縮12MBを96秒で受ける前提で、42秒の余裕がある（`behavior.md` 7章）。【推定】16.1MBの非圧縮なら転送129秒で、35＋129＋2＋5＝171秒、余裕は9秒に減る。gzip の実測（6章の4）で余裕を確かめる。
- 選んだ種別（最短時間／事故考慮）は再検索用に保持する（`frontend-spec.md:240`）。種別に「中間案」を足す。

### 4.3 中間案でナビ中に再検索した場合

再検索は安全な場所で止まってから行う明示操作である（`frontend-spec.md:299`）。新しい応答で `middle_id` が null になることがある。

- **推奨**：中間案がない場合は自動で別の経路に切り替えず、ナビを停止状態にして比較カードを表示する。利用者は止まっているので、ここで選び直してもらう。
- 代わりの案：事故考慮経路（null なら最短時間経路）に切り替えて、切り替えたことを表示する。操作は減るが、利用者が避けたかった遠回りに替わることがある。

### 5.2 配置

- 初期の選択は今の規則を変えない。中間案を初期選択や「おすすめ」にはしない。

### 6.1 測定1〜3の結果（2026-11-11）
