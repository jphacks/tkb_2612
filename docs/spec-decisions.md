## 確定：天候は除外条件にせず、経路評価の重み付けに使う

利用者の提案を受け、天候については当初の完全一致による絞り込みを変更する方針で合意した。

- 指定天候と一致しない事故も、経路評価の対象に残す。一致する事故の寄与を増やす。
- 時間帯・曜日区分など、天候以外の集計条件は今回の変更では変えない。
- APIは、他の指定条件を適用した経路周辺の事故について、天候を問わない事故件数・死傷者数と、指定天候に一致する事故件数・死傷者数を分けて返す。
- 指定天候に一致する事故が0件なら、一致する集計値はそのまま0件を返す。天候不一致の事故は引き続き評価対象になる。
- この方針は一致件数にかかわらず適用する。0件のときだけ条件を自動解除する処理は設けない。
- 重みの係数、計算式、経路決定への組込み方は、その後 [route-scoring-decision.md](route-scoring-decision.md) で暫定決定した（雨2倍、霧・雪4倍）。
- 2種類の集計のフィールド構成は `weather_match` として確定し、[api/openapi.yaml](api/openapi.yaml) と [frontend-spec.md](frontend-spec.md) へ反映した。

## 確定：条件に一致する事故がない場合

- 指定条件に一致する事故がない場合は、該当事故0件として返す。天候については、上記の合意により「指定天候に一致する集計値」と「天候を問わない集計値」を区別する。
- 全候補で0件であっても、条件を自動解除しない。時間帯・曜日区分の絞り込みを維持し、天候についても一致集計の条件を勝手に変更しない。
- 既存案の `api/behavior.md` 第7節にある条件の自動緩和は採用しない。
- PR #1には天候→曜日区分→時間帯の自動緩和が記載されているが、今回の「0件として返す」という個別合意と不一致である。統合時は自動緩和を行わない仕様に整合させる。
- この決定だけでは、事故0件の場合の経路選定方法や表示文言までは確定しない。それらは別途検証中の範囲に属する。

## 確定：死傷者数の集計範囲

- APIで返す死傷者数は、選択した移動手段が関わる事故の「事故全体の人数」を合計する。
- 例えば、自動車で検索した場合、自動車と歩行者の事故では歩行者側の死傷者も含める。
- 選択した移動手段と一致する当事者だけの被害人数としては扱わない。
- この合意は人数の集計範囲に関するもの。死者・負傷者に与える経路評価上の重みは別途検証の対象。

## 確定：座標・日時が不正な事故レコードの取り込み

- 座標や日時が欠損・不正な事故レコードは、その行を除外する。
- 不正な行があっても、残りのデータで前処理を続ける。
- 除外件数と原因を開発者向けに記録する。原因の例は、緯度・経度の空欄、存在しない日付など。
- この合意は行単位の座標・日時の不正に関するもの。ファイルを読めない、必須列がない、全行が除外された場合などの扱いは、この合意だけでは確定しない。

## 確定：GPSナビ機能の追加（利用者決定、2026-10-24）

利用者から、GPSを利用したリアルタイムナビ機能の追加を指定された。影響の検討で示した3段階（A：経路上の現在地・進捗・逸脱表示、B：危険区間への接近通知、C：曲がり角ごとの案内と自動再検索）のうち、**A＋B＋模擬走行モード**を採用する。Cは採用しない。

- ナビを開始できるのは選定2経路（最短時間経路・事故考慮経路）のみ。未選定の候補からは開始しない。
- 段階A：選んだ経路の上に現在地を継続表示し、残り距離・残り時間と、経路から外れたことを表示する。現在地と経路の照合はブラウザ内で行い、ナビ中の現在地を定期的にサーバへ送らない。
- 段階B：危険区間に近づいたら、画面表示と音声読み上げで通知する。表示用の上位100区間（`high_risk_sections`）は流用せず、ナビ用に別の区間データを定義する。
- 経路から外れた場合は、外れたことを表示し、再検索ボタンを示す。利用者が押したときだけ現在地から再検索する。自動再検索はしない。
- 模擬走行モード：選んだ経路の上を、所要時間に合わせた速度で自動移動させる。倍速・一時停止・位置の揺らぎを持つ。実機GPSと同じナビ処理を通す。記録した軌跡ファイルの再生は今回の範囲外とする。
- 曲がり角ごとの案内（OSRMの `steps` の取得）、自動再検索、バックグラウンド追跡、位置履歴の保存は行わない。
- **追加の決定（2026-10-24）：検索を中止するボタン（明示的な中止操作）は設けない。** 通常の経路検索にも、ナビ中の再検索にも置かない。レビューで、route期限を180秒に延ばしたために通常検索で最大180秒入力を変更できなくなると指摘された。その対策として提案された中止ボタンは、利用者が採用しなかった。検索中は期限まで応答を待つ。ページの非表示などによる中断の規則は変えない。
- **追加の決定（2026-10-24）：現在地と経路の照合（経路上の位置・進行方向の推定）は、仕様では満たすべき条件とテストケースで規定し、具体的な計算手順は実装時にテストを通して決める。** 計算手順を文章で規定する方式では、レビューのたびに新しい反例（GPSの揺らぎによる誤確定など）が見つかったため、この方式に切り替える。修正作業は利用者の指定によりGPT-6 Astraが担当する。
- **追加の決定（2026-10-25）：ナビの開始と模擬走行・接近通知の表示を次のように変える。**
  - ナビの開始操作は、地図上の経路カードにある紙飛行機のボタン（PR #18で配置済み）とする。押した後の7.9の注意確認は従来どおり必須。
  - 模擬走行の画面（開始操作、SimulationControls、常設表示）は、ビルドフラグ `VITE_ENABLE_SIMULATION` を有効にしたビルドだけに含める。フラグのない本番ビルドでは模擬走行を機能として出さず、実機GPSだけで開始する。模擬位置源のコードと、判定器の受け入れテスト（M1〜M11）は残す。デモ用のイメージはフラグを有効にしてビルドする。
  - ナビ中の危険区間への接近通知は、地図の上のポップアップで表示する。ナビ開始前の結果画面は変えない。ポップアップは7.9の受動表示の条件（閉じる操作を必須にしない、フォーカスを奪わない、現在地や操作を隠さない）を守り、ナビ用の `sections` だけを使う。位置は地図の下端に固定する。
  - 最短時間経路と事故考慮経路が同じIDのときは、紙飛行機ボタンから開始したナビの選定種別を事故考慮経路とする。
  - ナビを開始してもサイドバーを自動で開かない（PR #18 の、サイドバーは利用者が開いたときだけ表示する方針に合わせる）。サイドバーを閉じたナビ中の地図に見えるのは、地図と現在地、接近通知、模擬走行中の表示（模擬走行のときだけ）、追従を戻すボタンでよい。状態・残り距離/時間・停止などの操作と、7.5の「過去事故の参考情報で、安全を保証しない」旨の表示はサイドバーの中に置く。この旨を地図上に常設しないことは、7.5・11章の常設の要件からの変更である。

この決定はフロントエンドの範囲を含む。「今回の対象」でフロントエンドを確定対象から外した扱いの例外として、ナビ機能の振る舞いに限って確定する。警告の距離、ナビ用区間データの形式、逸脱の判定基準などの技術的な細部は、これまでどおりGPT-6.1 Solに委任する。委任判断は[backend-delegated-decisions.md](backend-delegated-decisions.md)と同様に利用者決定と区別して記録する。
