# フロントエンド機能仕様

## 1. 目的と責任範囲

React / TypeScript / Vite / MapLibre GL JSで、出発地と目的地を指定し、最短時間経路と事故履歴を考慮した経路を比較する。API契約は [api/openapi.yaml](api/openapi.yaml)、集計の意味は [api/behavior.md](api/behavior.md) に従う。生成されたTypeScript型を使用し、リスク集計・候補選定・条件緩和をフロントで再計算しない。

現行機能の根拠は [app/static/app.js](../app/static/app.js) と [index.html](../app/static/index.html)。住所選択、地図指定、条件指定、2経路比較、全候補一覧、事故点表示、警告を引き継ぐ。GPSによる出発地設定、PWA、出発日時の指定、曜日区分、時間帯・曜日区分・天候の自動設定は移行追加。現行UIのLeaflet、配色、線幅、装飾は移植要件ではない。

**本書は機能だけを規定する。色・フォント・余白・アイコンの絵柄・線の見た目・細かいレイアウトは決めない。** 後のデザイン作業で決定する。画面を操作可能にする最低限の意味構造だけを作り、装飾を持たない最小コンポーネントを基本にする。

未指定の両地点は空。地図の初期中心は現行同様東京駅相当 `[139.7671,35.6812]` とし、初期表示で位置許可を要求しない。ズーム・画面寸法はデザイン段階に委ねる。

## 3. 状態モデルと操作フロー

住所入力の文字列と確定座標を別に持つ。「住所が入力済み」だけでは確定としない。各地点はinputText、selectedPoint（lat/lonとlabelまたはnull）、検索候補、検索状態、入力revisionを持つ。

全体は次を持つ。

- 選択対象
- 出発日時（mode: now/custom、custom時の日時）
- 条件（period/day_type/weatherはそれぞれ値とsource: auto/manual。weatherのautoには取得状態と取得元情報を付ける）
- 条件取得状態と世代番号
- ルート状態、結果
- health状態、地図状態、GPS状態、事故点表示状態

保存先はReact等のページ内メモリのみ。

| イベント                         | 必須挙動                                                                                                                                                                                  |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 初回表示                         | `/api/health` を1回呼ぶ。出発日時=現在で `/api/conditions` を地点なしで呼び、period/day_typeを自動設定する。weatherは地点未確定のためすべて。地図初期化を並行してよい。空の比較案内を表示 |
| 住所編集                         | その地点の確定座標・マーカー・候補を解除し、revisionを更新。経路結果と経路/事故/高リスクレイヤーを消す                                                                                    |
| 住所検索ボタン/Enter             | trim後2〜200文字を検査してGET `/api/geocode?q=...`。入力中の自動問い合わせなし                                                                                                            |
| 住所結果選択                     | 座標・labelを確定、マーカー更新、候補を閉じ、結果を消す。地図を地点へ移動し、次の地図指定対象を反対側に切り替える。両地点が確定したら条件取得（4章）を行う                                |
| 地図指定対象ボタン               | origin/destを明示選択。選択中の対象を操作・支援技術に伝える                                                                                                                               |
| 地図クリック/タップ              | 選択対象へ座標を確定。住所表示を地図指定と座標に置換し、結果を消す。次の対象を反対側へ切替。両地点が確定したら条件取得を行う                                                              |
| 出発日時変更                     | 時間帯・曜日区分・天候の手動指定を解除して自動に戻し、条件取得を行う。結果を消す                                                                                                          |
| 時間帯・曜日区分・天候の手動変更 | その項目をmanualにし、以後の自動取得で上書きしない。結果を消す。「自動に戻す」操作で即座に条件取得を行う                                                                                  |
| mode・許容追加時間の変更         | 以前の比較結果とその地図レイヤーを消す。確定地点は保持。検索を自動実行しない                                                                                                              |
| 経路検索                         | 両地点確定を確認する。出発日時=現在で、最後の条件取得から15分以上経過していれば、条件取得を完了してからPOST `/api/route`。既存比較を消し、検索中へ移行                                    |
| 検索成功                         | 両選定IDを候補から解決して比較と地図を更新、2経路全体が入る範囲へ移動                                                                                                                     |
| 検索失敗                         | メッセージと再試行操作を提示、入力は保持。古い結果を現条件の結果として残さない                                                                                                            |
| 事故点表示切替                   | 描画だけ切替。APIを呼ばず、統計・高リスク区間は変更しない                                                                                                                                 |

### 抑止と競合の制御

ルート検索中は条件入力、出発日時、地点変更、住所検索、GPS、二重送信を抑止する。地図のパン/ズームや比較と無関係な操作は可能。

住所検索中は当該検索ボタンを抑止するが、編集は可能。条件取得中は経路検索ボタンを抑止するが、各条件の手動変更は可能。手動変更した項目は応答到着時に上書きしない。

住所検索要求・条件取得要求ごとにsequenceとrevisionを保持し、遅い旧応答（エラーも含む）を反映しない。地点確定・条件変更・出発日時変更・経路検索開始・unmount時は不要な通信をabortする。abortが間に合わなくても応答世代照合で棄却する。ボタンの再有効化も現行要求の完了時だけ行う。

経路応答は取得時の入力snapshotと世代番号に対応付ける。地図がAPIより遅く初期化されても、最新結果を後から描画できるようにする。healthのdataset_idと後続routeのdataset_idが違う場合はrouteを表示しつつhealthを1回更新する。事故点のID集合を別データ世代へ持ち越さない。

## 4. 出発日時と条件の自動設定（移行追加）

旅行計画など将来の移動の比較を想定し、出発日時・時間帯・曜日区分・天候を変更可能とする。既定は「現在の時間帯・曜日区分と、該当地域の現在の天候」とする。

### 出発日時

- 「現在」と「日時指定」を選択できる。日時はAsia/Tokyo固定で扱い、ブラウザのタイムゾーンに依存しない。
- 「現在」の基準時刻は条件取得のたびにその時点の時刻とする。表示には取得時の基準時刻を示す。
- 過去の日時も指定できる。この場合、天候の自動取得は行わず、天候はすべてにして手動選択を案内する。
- 出発日時はroute APIへ送らない。routeへ送るのはそこから決まったperiod/day_type/weatherだけである。

### `/api/conditions`

時間帯・曜日区分・天候の自動値は `/api/conditions` から取得する。区分境界と祝日判定を事故集計側と一致させるため、フロントでは計算しない。

```
GET /api/conditions?datetime=<ISO8601, +09:00>[&lat=..&lon=..]
→ {
  period: <時間帯値>,
  day_type: <平日|休日>,
  day_type_reason: "土曜" | "日曜" | "祝日：<名称>" | "振替休日" | "平日" | ...,
  holiday_table_covered: boolean,
  weather: <晴|曇|雨|霧|雪> | null,
  weather_status: "ok" | "no_location" | "out_of_range" | "past" | "unavailable",
  weather_source: { provider, target_time, kind: "current"|"forecast" } | null
}
```

具体的な型はOpenAPIで確定する。フロントの扱いは次のとおり。

- 両地点が確定していなければlat/lonを付けない。その場合、天候は `weather_status=no_location` となる。
- 両地点が確定したら、2地点の中点を**小数2桁（約1km）に丸めて**送る。2地点の直線距離は最大30kmであり、中点1点で地域を代表させる。
- 出発日時=現在の場合、天候は現況値になる。未来の日時の場合は、その時刻の毎時予報になる。予報範囲外の日時は `out_of_range` として天候をすべてにする。
- `holiday_table_covered=false`（祝日表の収録範囲外）の場合、曜日区分は土日だけで判定された値である旨を警告として表示する。
- 取得失敗・タイムアウト（10秒）・オフラインの場合、auto状態の項目はすべてにして、失敗と手動選択を案内する。経路検索は妨げない。自動リトライはしない。

### 自動値の表示

- 各項目について、自動値か手動値かを表示する。自動の天候には取得元、対象時刻、現況か予報かを示す（例：「自動：雨（Open-Meteo、10/31 14:00の予報）」）。
- 曜日区分にはday_type_reasonを表示する（例：「休日（祝日：文化の日）」）。
- 事故記録の天候は発生時の現場の判定であり、自動取得の天候は気象モデルの推定値である。両者が同じ尺度でないことを説明に含める。
- 天候の自動取得が使えない理由（地点未確定・予報範囲外・過去日時・取得失敗）はweather_statusごとに区別して伝える。

### プライバシー

外部の気象サービスへ座標を送るのはサーバであり、ブラウザから直接は呼ばない。座標が自サーバへ送られるのは次の2つの場合だけである。

- 両地点の確定後に行う条件取得（丸めた中点のみ）
- 利用者が行う経路検索

## 5. API通信と表示規則

APIは同一オリジンの相対 `/api/...` を使い、Accept application/json、routeはContent-Type application/json。UIタイムアウトはroute/geocode/healthが現行同様45秒、conditionsが10秒。自動リトライ、自動ポーリング、入力ごとの住所補完は行わない。health失敗は手動再確認、経路失敗は明示的再検索とする。

応答がJSONでない、必須フィールド/参照IDが壊れている場合は「応答を読み取れない」と表示し、部分的な成功として描画しない。未知のerror.codeはmessageと再試行案内で扱う。codeで状態を判断し、日本語messageの部分一致で処理を分岐しない。AbortControllerによる期限超過、ネットワーク不通、HTTPエラーを区別して利用者に伝える。提供元ラベル・API説明・エラーはテキストとして描画し、HTMLとして挿入しない。

healthが503 data_unavailableなら経路検索を無効化し、データ準備中と再確認操作を示す。healthのネットワークエラーだけなら「状態未確認」として入力・手動経路検索を許す。healthは上流サービスが利用可能という保証ではない。

### 比較表示

- 「最短時間経路」と「事故考慮経路（取得候補内）」の2つの意味を常に表示する。事故考慮は全道路網の最適解という表現にしない。
- 各経路について次を表示し、単位を明示する。表示丸めで選定や許容内外を再判定しない。
  - duration：分（小数1桁）
  - distance：km（小数2桁）
  - extra_minutes：分（小数1桁）
  - 事故件数、死亡/負傷事故件数、死者/負傷者の人数
  - weighted_risk、risk_per_km
- risk_reduction_percentがnullなら「算出できません（最短時間経路の基準リスクが0）」と表示し、0%や100%へ変換しない。数値なら小数1桁の%表示。
- reason、全warnings、risk_noteを省略しない。要求条件（period/day_type/weather）とeffective_conditionsが違う場合、解除した条件を明示する。exact_condition_countも全候補詳細で確認可能にする。
- 適用条件の表示に、要求時の出発日時と、各条件が自動か手動かを含める。
- 半径radius_m、候補数、aggregation_ms（表示は整数ms可）、対象データ年を確認できるようにする。aggregation_msを検索全体の通信時間と表示しない。
- 最短時間と事故考慮が同じIDでも2つの選定の意味を表示し「今回は同じ経路」と伝える。別々の改善があるように見せない。

## 6. MapLibreのデータ・レイヤー契約

経路の `geometry` はLineString、事故と高リスク区間はFeatureCollectionなので、座標反転や再集計なしでGeoJSON sourceに設定する。MapLibreのsource更新機能を使用する（[公式GeoJSONSource](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/)）。以下のIDをフロント内の標準とし、データと描画スタイルを分離する。

| Source / layer ID                         | 型・内容                                              | 更新条件                                          |
| ----------------------------------------- | ----------------------------------------------------- | ------------------------------------------------- |
| route-fastest / route-fastest-line        | fastest.geometry、line                                | 経路成功時と結果解除時                            |
| route-safest / route-safest-line          | safest.geometry、line                                 | 同上。同一IDなら重なりを含めて2選定の意味を伝える |
| route-high-risk / route-high-risk-line    | 選定経路2本のhigh_risk_sectionsを連結したFC、line     | 同じ経路は一度だけ追加                            |
| route-accidents / route-accidents-point   | 選定経路2本の事故FCをidで重複排除したFC、circle等の点 | 応答/表示切替。候補順で最初の点を採用             |
| origin-marker / dest-marker               | それぞれの確定座標                                    | 地点確定・解除                                    |
| current-location / current-location-point | 直近に取得したGPS位置、任意の精度表示                 | GPS取得・地点変更・終了                           |

背景地図→経路→高リスク区間→事故点→地点マーカーの論理順で、操作に必要なマーカーが隠れないようにする。経路間の重複を判別する表現はデザイン段階で決める。色の指定はしない。地図上の役割は凡例/テキストでもわかるようにする。

事故点のポップアップは次を表示する。

- 死亡/負傷区分（deaths>0）
- 発生日と曜日区分（平日/休日）
- 時間帯、天候
- 死者/負傷者人数
- source_year

dateはYYYYMMDD整数から年月日へ表示変換し、source_yearと混同しない。事故点の曜日区分は応答の値を表示し、フロントで日付から判定しない。高リスク区間の操作でweighted_riskと対象経路を確認できる。地図上の点数は重複排除後なので、各経路のpoints_shownの単純合計と異なってよい。集計値は変更しない。

既存source/layerを更新してMapインスタンスの作り直しを避ける。結果解除時に古いsourceデータ/ポップアップを消す。コンポーネント終了時にイベントとMapを破棄する。背景スタイル再読込時は最新source/layerを復元する。地図のbounds計算は選定2経路だけを使い、事故点の広がりや未選定候補で勝手に範囲を変えない。

## 7. GPSによる出発地設定（移行追加）

「現在地を出発地に設定」の明示操作で、`navigator.geolocation.getCurrentPosition` を1回呼ぶ。位置情報は利用者の許可とsecure contextが必要である（[W3C Geolocation](https://www.w3.org/TR/geolocation/)）。本番はHTTPS必須。localhost例外に依存する構成を本番へ持ち込まない。

初期契約の取得オプションはenableHighAccuracy=true、timeout=10000ms、maximumAge=0。これは取得要求でありGPSセンサー使用や精度を保証しない。現在地は緯度経度WGS84、accuracyはmとして扱う。

成功時は有限数値・日本矩形内かを確認し、出発地を「現在地」として確定する。精度（accuracy）を利用者が確認できるようにし、精度による隠れた座標補正・切り捨てはしない。経路結果を解除するが目的地は保持する。地図があれば移動してマーカー更新。目的地が確定済みなら4章の条件取得を行う。自動で経路検索・住所逆引きをしない。座標がサーバへ送られるのは4章の条件取得（丸めた中点）と利用者の経路検索のときだけ。

許可拒否(PERMISSION_DENIED)なら明確に説明して住所/地図指定を案内し、許可ダイアログを反復させない。取得不能(POSITION_UNAVAILABLE)、timeout、非対応、非HTTPS、日本範囲外は区別し、既存の出発地を消さない。取得中に入力が変更されたら古い結果を棄却する。ブラウザによって取得要求自体はキャンセルできないため、世代管理を必須とする。

今回はwatchPosition、バックグラウンド追跡、位置履歴、区間接近通知、自動再ルート検索を実装しない。将来追加時は別の明示的開始/停止、clearWatch、電池/通信制御、提供元への送信頻度、精度誤差と区間データの網羅性を設計する。既存上位100区間を完全な警告対象一覧と扱わない。

## 8. PWA（移行追加）

- `/manifest.webmanifest` にname/short_name、start_url=/、scope=/、display=standalone、192×192と512×512のインストール用アイコンを設ける。アイコンの見た目・名称の最終文言はデザイン工程で決める。アイコンは内容ハッシュ付き `/assets/` に置く。
- `/sw.js` をscope=/で登録し、version付きアプリシェルのキャッシュだけを管理する。初回オンライン読込後にHTML・JS・CSS・自アプリの必要アセットをオフライン表示できること。
- `/api/*`（`/api/conditions` を含む）は成功/失敗ともService Worker・Cache Storageの対象外とする。住所入力、GPS位置、出発日時、条件取得結果、経路、事故点レスポンスをIndexedDB/localStorage/sessionStorage/URL履歴へ保存しない。Background Syncで再送しない。
- 地図タイル/スタイル/外部フォント等の外部リソースを一括保存・先読みしない。PWA化はオフライン地図/検索を意味しない。契約済み自己配信タイルのオフライン化は別要件。
- SW更新があれば利用者へ再読込可能と伝える。検索/GPS取得中に強制切替せず、同意した再読込時にメモリの位置・経路・条件が消えることを説明する。旧シェルcacheを更新完了後に削除し、型の異なるAPIと古いUIの混在はapi_version検査で検出する。
- インストール可能なブラウザには導線、非対応には通常Web利用を提供する。位置許可やインストールを初回表示で強制しない。対象ブラウザ/OSの厳密なサポート範囲は**要確認**。暫定受け入れは現行安定版のChromium系、Firefox、Safariで通常Web機能を確認し、PWAインストール可否は各環境の機能差として扱う。

## 9. スタイルを持たない最小構成

次の責務で最小限に分割し、汎用デザインシステムや装飾部品の大量作成はしない。

| コンポーネント                   | 責務                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| App                              | 状態とAPI操作の調整、画面単位のライフサイクル                                          |
| LocationInput（origin/dest共用） | 住所入力、候補、座標、地図指定対象、出発地のみGPS操作                                  |
| DepartureTimeInput               | 出発日時の「現在」/日時指定                                                            |
| RouteConditions                  | mode/period/day_type/weather/max_detour_minと送信操作。自動/手動の区別と「自動に戻す」 |
| MapView                          | MapLibreの生成、source/layer更新、地点選択イベント通知                                 |
| RouteComparison                  | 選定2本の指標・理由・適用条件と全候補詳細                                              |
| StatusMessages                   | ロード/空/警告/失敗を意味構造付きで通知                                                |
| DataAttribution                  | データ年・件数・帰属と参考指標の説明                                                   |

APIラッパー、入力世代管理、条件取得（自動/手動のマージ）、GPS、単位/日付の表示変換はUI描画から分離する。API型を部品ごとに再定義しない。semantic HTMLと必要なariaを先に実装する。MapLibre自身が必要とする基礎CSSは読み込んでよいが、独自の見た目は組み込まない。

後から差し替え可能なCSS変数のデザイントークン層を1か所に設ける方針とする。トークンの最終名・値は後決め。コンポーネント内へ色/フォント/余白/アイコンの見た目を直書きしない。MapLibreのpaint/layoutはCSSを直接継承しないため、同じトークン設定を読む地図スタイルアダプタを別に置き、更新時にsetPaintProperty等へ反映する。機能状態（最短/事故考慮/高リスク/死亡）と見た目の値を分離する。

## 10. データの帰属

DataAttributionに次を表示する。

- 事故データ：警察庁交通事故統計オープンデータ（対象source_year）
- 気象データ：Open-Meteo（CC BY 4.0、「Weather data by Open-Meteo.com」とリンク）
- 祝日データ：内閣府「国民の祝日」
- 地図・経路・住所検索の各提供元

Open-Meteoの無料APIは非商用利用に限られる。製品化する場合は有償プランへ切り替えるか、提供元を変更する。

## 11. フロント受け入れ基準

OpenAPI由来のfixtureで、次の応答パターンを確認する。

- 通常2本・同一経路・1候補・緩和・全0・間引き・全エラー・地図失敗

次の競合・状態遷移を含める。

- 遅い住所応答/エラー、地図初期化との競合、連続操作
- 条件変更後の古い結果、dataset変更

出発日時と条件について、次を確認する。

- 現在/日時指定の切替
- 時間帯の各境界（3:59/4:00、8:59/9:00、15:59/16:00、18:59/19:00、23:59/0:00）
- 平日・土日・祝日・振替休日・祝日表範囲外の曜日区分
- 天候の現況/予報/予報範囲外/過去日時/地点未確定/取得失敗
- 手動値が自動取得で上書きされないこと、「自動に戻す」
- 出発日時変更による自動への復帰
- 古い条件応答の棄却
- 現在モードで15分経過後の検索時の再取得
- 条件取得に送る座標が丸めた中点だけであること

GPSについて、次を確認する。

- 成功/拒否/timeout/非対応/古い応答

PWAについて、次を確認する。

- オンライン初回/オフライン再訪/更新

API/座標/条件取得結果が永続ストレージにないことも確認する。見た目のスナップショット一致は今回の受け入れ条件にしない。
